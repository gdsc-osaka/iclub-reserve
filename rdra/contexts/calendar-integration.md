# BIZ-005: カレンダー連携

承認済み予約のGoogle Calendarへの自動登録・更新・削除と、団体のメンバーに自団体の予約をカレンダーとして届けることを担うコンテキスト。

Google Calendarは購読URLを知っていれば誰でも閲覧できるため、COND-008の3段階のうち最も狭い開示範囲——施設名と日時だけ——を載せる。どの団体が使っているかは学内の利用者どうしで共有すれば足りる情報であり、外部に出す必要はないためである。

施設ごとのカレンダーの購読URLは事務局にだけ出す（REQ-030）。施設がいつ埋まっているかを見渡したいのは事務局で、団体のメンバーにとっては他団体の予約が混ざるだけだからである。団体のメンバーには、自団体の予約だけを載せたカレンダーを別に届ける（REQ-050）。

## カレンダーの持ち方

カレンダーは、事務局が引き継いで管理できる共有のGoogleアカウントで作る（REQ-026）。運営するのは学生であり、作った人の個人アカウントに置くと、その人が卒業したときにカレンダーを管理できる人がいなくなるためである。

システムはGoogle Service Accountを使い、予定の登録・更新・削除だけを行う。カレンダーの作成・公開設定は人が行う。施設を追加するときの手順は次のとおり。

1. 共有のGoogleアカウントで、施設・設備ごとのカレンダーを作る。
2. カレンダーを一般公開する。
3. Service Accountのメールアドレスに「予定の変更」の権限を共有する。
4. 施設管理画面（SCR-009）で、そのカレンダーのIDを施設に設定する。保存するときに、システムが予定を書き込めることを確かめる（COND-025）。

## 同期の考え方

予約の操作ごとに「登録せよ」「削除せよ」と命令を送るのではなく、予約の今の状態を見て、カレンダーをそれに合わせる（COND-024）。EVT-009・EVT-010・EVT-011は、合わせた結果として行う操作の種類である。こうしておくと、承認の直後にキャンセルされるなど操作が続いても、同期の順番に関わらず最後は正しい状態になり、失敗した同期をやり直しても予定が二重にならない。

予定のタイトルは施設名とする。施設ごとのカレンダーを1つにまとめて表示する使い方（利用者が複数のカレンダーを重ねて見る場合や、将来すべての施設をまとめたカレンダーを用意する場合）でも、どの施設の予約かが予定だけで分かるようにするためである。

施設の名称の変更やGoogle Calendar IDの設定・変更、日次の突き合わせのように、多くの予約をまとめて反映する処理は、終了日時が前日0時以降の予約だけを扱う。過去の予約まで遡ると、件数に比例して処理が重くなるためである。

## 自団体の予約の購読

自団体の予約は、Google Calendarに書き込まず、システムがiCal形式で配信する。カレンダーアプリが購読URLを読みに来るたびに、その時点の予約から組み立てて返す（COND-029）。Google Calendarを使わないのは、次の理由による。

- 施設のカレンダーと同じ作り方では、団体が増えるたびに事務局がカレンダーを作り、Service Accountに共有し、IDを登録する手間がかかる。
- 自団体の予約は団体のメンバーだけが見る情報なので、施設のカレンダーのように一般公開できない。限られた人に共有するには一人ずつGoogleアカウントを登録する必要があり、学内のメールアドレスがGoogleアカウントとは限らない。
- 配信のたびに予約から組み立てれば、同期・再試行・突き合わせ（COND-024）が要らず、カレンダーはいつも予約の今の状態になる。

カレンダーアプリはログインできないので、購読URLそのものが鍵になる。URLを利用者と所属の組ごとに分けるのは、団体を抜けた人のURLだけを止め、URLが漏れたときも本人が作り直すだけで済むようにするためである。団体で1本にすると、抜けた人が見続けられ、止めるには全員に購読をやり直してもらうことになる。

URLで読めるのは自団体のメンバーが見てよい項目で、備考も含む（COND-029 の (3)）。その代わり、URLが漏れると備考まで読まれてしまう。URLを人に教えないよう画面で案内し、漏れたときは作り直しで止める。

```mermaid
            システム->>GC: 変更前の施設のカレンダーから削除（EVT-010）
        end
    else 事務局が施設の名称・Google Calendar ID を変えた（UC-015）
        事務局->>システム: 施設管理画面（SCR-009）で保存
        システム->>システム: その施設の承認済み予約のうち、終了日時が前日0時以降のものを選ぶ
        システム->>GC: 名称の変更は予定を更新（EVT-011）、ID の設定・変更は新しいカレンダーに登録（EVT-009）
    else 1日1回の突き合わせ
        システム->>GC: 各施設のカレンダーの予定を取得（終了日時が前日0時以降）
        システム->>システム: 承認済み予約と比べる（システムが登録した予定だけ）
        システム->>GC: 登録漏れは登録（EVT-009）、余分な予定は削除（EVT-010）、食い違いは更新（EVT-011）
    end
    Note over システム,GC: 同期に失敗しても予約の操作は失敗させない。失敗した同期は再試行し、残ったずれは翌日の突き合わせで直す
```
