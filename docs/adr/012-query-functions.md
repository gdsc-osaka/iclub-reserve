# ADR-012: 素通しの読み取りは、ポートとユースケースを持たない関数 1 本にする

## ステータス

提案 (2026-10-16)

ADR-001 の決定 1・6・7 のうち、**素通しの読み取り**（決定 2 で定める）についての部分を置き換える。
ADR-001 のそれ以外（読み取りを Repository から分ける・入口ごとのフォルダ分け・読み取りモデルは重複してよい）は変えない。

## コンテキスト

ADR-001 は、読み取りの層の形を Repository と「完全に同一」にし（トレードオフの表）、
読み取りでもユースケースを省かない（決定 7）と決めた。その結果、画面の読み取り 1 本ごとに次のファイルと配線が付く。

| 置き場所                                   | 中身                                          |
| ------------------------------------------ | --------------------------------------------- |
| `app/query/<入口>/<出口>.ts`               | 型と、Query ポートの interface                |
| `app/infra/<集約>/<出口>-query.ts`         | SQL（`create<出口>Query(db)`）                |
| `app/infra/<集約>/<出口>-query-d1.test.ts` | 本物の D1 で SQL を確かめる                   |
| `app/usecases/<集約>/get-<出口>.ts`        | 門番と、Query の呼び出し                      |
| `app/usecases/<集約>/get-<出口>.test.ts`   | 偽物の Query を渡して、ユースケースを確かめる |
| ルート                                     | `{ xxxQuery: createXxxQuery(db) }` の配線     |

2026-10-15 の時点で、読み取り側は合わせて約 1.28 万行あった
（ポート 1,545・infra の `*-query.ts` 2,659・その D1 テスト 1,897・読み取りのユースケース 1,996・そのテスト 4,739）。
たとえば事務局のダッシュボードの「今日の予約状況」は 5 ファイル 399 行で、
中身は SQL の約 40 行と、事務局かどうかの判定 1 行だった。

多くの読み取りについて、次のことが言える。

1. **ユースケースが素通しである。** 「事務局でなければ Forbidden、そうでなければ Query の結果をそのまま返す」だけのものが多い。
   同じ `if (!args.isStaff) return errAsync(...)` が 8 本のユースケースに書き写されていた
   （AGENTS.md の「同じ判定を 2 つのユースケースに書き写さない」にも反する）。
2. **ユースケースのテストが、ほとんど何も確かめていない。** 偽物の Query が返した値をそのまま返すか、を見ているだけである。
   読み取りの誤りはほぼ SQL の側にあり、それは D1 のテストでしか見つからない
   （`app/query/user/user-group-list-d1.test.ts` の冒頭に、型もユースケースのテストも通ったまま、どの団体も「メンバー 0 人」になっていた事例がある）。
3. **ポートを差し替える場面が無い。** Repository のポートは、書き込みの業務の判断を DB 抜きで試すためにある。
   素通しのユースケースには試す判断が無いので、ポートが役に立つ場面が無い。

つまり、読み取り 1 本あたりの行数の大半は、SQL でも業務の判断でもなく、層をまたぐための手続きだった。

## 決定

### 1. 素通しの読み取りは、`app/query/` の関数 1 本にする

型・門番・SQL を `app/query/<入口>/<出口>.ts` の 1 ファイルに置き、`find*(db, args)` の関数として公開する。
ポートの interface・`app/infra/` の実装・ユースケースは作らない。
本体はユースケースと同じく `safeTry` に平らに並べ、門番を先頭に置く。門番で止まれば、問い合わせは組み立てもしない。

```ts
// app/query/reservation/staff-today-schedule.ts
export interface StaffTodaySchedule {
  readonly facilities: readonly TodayScheduleFacility[];
  readonly reservations: readonly TodayScheduleReservation[];
}

export const findStaffTodaySchedule = (
  db: Database,
  args: FindStaffTodayScheduleArgs,
): ResultAsync<StaffTodaySchedule, QueryError> =>
  safeTry(async function* () {
    yield* ensureStaff(args.isStaff, "事務局ではない人が、今日の予約状況を取得しようとした。");

    const facilitiesQuery = db.select(/* ... */).from(facilityTable); /* ... */
    const reservationsQuery = db.select(/* ... */).from(reservationTable); /* ... */

    const [facilities, reservations] = yield* ResultAsync.fromPromise(
      Promise.all([facilitiesQuery, reservationsQuery]),
      (error): QueryError => ({ code: QueryErrorCode.DatabaseError, message: "...", cause: error }),
    );
    return ok({ facilities, reservations });
  });
```

ルートは関数を呼ぶだけになる。

```ts
const result = await findStaffTodaySchedule(db, { isStaff: user.is_staff, now });
```

ADR-001 は「SQL を書いてよいのは infra だけ」としていたが、これを改め、`app/query/` にも SQL を書いてよいことにする。
読み取りの SQL は、その画面の型と同じファイルにあるほうが追いやすい。
複数の読み取りで使う SQL の部品（`hasOverlappingReservation`・`memberCountsByGroup`・`toUnreadRows` など）は
今の `app/infra/<集約>/` に置いたまま、`app/query/` から読み込む。

### 2. 「素通し」の範囲 ― ユースケースを残す読み取り

関数 1 本にしてよいのは、次の 3 つをすべて満たす読み取りである。

- 見る人の判定が、Repository を読まない門番 1 つで済む（事務局かどうか・本人の分だけを読むか）
- 見る人によって、返す形が変わらない
- 読むのと同時に書き込まない

どれかを満たさないものはユースケースを残し、今までどおり ADR-001 の形で書く。

| ユースケース                | 残す理由                                                                           |
| --------------------------- | ---------------------------------------------------------------------------------- |
| `get-reservation`           | 予約を読んでから所属を引いて判定し、詳細を見られない人には項目を落とす（COND-008） |
| `get-reservation-list`      | 所属団体を読んでから、絞り込む団体と並び順を決める                                 |
| `get-group-management`      | 所属と役割を読んで判定し、管理できない人にはメールアドレスを落とす                 |
| `get-availability-calendar` | 予約 1 件ごとに、見る人の所属に応じて見せる項目を決める（COND-008）                |

### 3. 画面に合わせた数え上げは、純粋な `to*` 関数に分ける

「先頭 5 件と総数」のように、SQL の結果を画面の形に整える処理は、同じファイルの `to*` 関数に書く（AGENTS.md の接頭辞の表）。
業務の数字と判定はドメインの定数・関数を使う（`STAFF_PENDING_RESERVATIONS_LIMIT`・`isShortNotice` など）。
「7 日を切っているか」のような境目のある数え方は、この `to*` 関数を DB なしの単体テストで確かめる。

### 4. 事務局かどうかの門番は `app/query/_shared/` に置く

`ensureStaff(isStaff, message)` を `app/query/_shared/staff.ts` に置き、`QueryError` の Forbidden を返す。
読み取りごとに違うのはログ用の説明だけなので、それを引数で受け取る（AGENTS.md の `ensureNotLastAdmin` と同じ流儀）。

### 5. テストは D1 のテストと、`to*` の単体テストだけにする

- `app/query/<入口>/<出口>-d1.test.ts` に、SQL の確認と、門番が止めることを書く。
- `to*` 関数があれば、`app/query/<入口>/<出口>.test.ts` に DB なしの単体テストを書く。
- 偽物の Query を渡すテストは書かない。

### 6. 画面の部品は、型だけを `import type` で読み込む

`app/query/` のファイルは Drizzle と `~/infra/` を読み込むようになる。
`tsconfig.json` は `verbatimModuleSyntax` なので、`import type` で型だけを読み込めば、ブラウザ向けのバンドルに DB のコードは入らない。
画面の部品（`app/components/`・ルートの部品）からは、`app/query/` の値（関数・定数）を読み込まないこと。

### 7. 新しく書く読み取りはこの形で書き、既存のものは触るときに移す

一度にすべてを書き換えない。まず事務局のダッシュボードの 4 本
（今日の予約状況・承認待ちの予約・団体からの未読メッセージ・承認待ちの団体）を、この ADR と同じ変更で移した。

### 8. 判断を持つユースケースもポートで使う読み取りは、ポートを残して関数を呼ぶ

素通しの読み取りの中には、判断を持つユースケースが同じ読み取りをポートで使っているものがある。
所属団体の一覧は `get-reservation-list` など 6 本が、団体側の未読は「すべて確認済みにする」（`mark-all-reservations-read`）が使っている。
これらのユースケースは、偽物のポートを渡して判断を試しているので、ポートは残す。

このときは、SQL を決定 1 の関数に置き、ポートの実装 `create<出口>Query(db)` はその関数を呼ぶだけにして、同じファイルに置く。
SQL を 2 か所に書かず、`app/infra/` に実装のファイルを残さない。画面のための読み取りは、ルートから関数を直接呼ぶ。

```ts
// app/query/user/user-group-list.ts
export const createUserGroupListQuery = (db: Database): UserGroupListQuery => ({
  findByUserId: (userId) => findUserGroupList(db, { actorUserId: userId }),
});
```

## 理由

### 案 A: 今のまま（却下）

コンテキストのとおり、読み取り 1 本ごとに 5 ファイルと配線が付き、その大半が手続きである。
読み取りは画面の数だけ増えるので、このままでは画面を足すたびに同じ量の手続きが増え続ける。

### 案 B: ポートは残し、ユースケースだけを省く（却下）

ルートが `createXxxQuery(db)` を作って直接呼ぶ。行数はいくらか減るが、門番の置き場所が無くなる。
ルートに書けば AGENTS.md の「ユースケースが持っている判定をルートに書き写さない」に反し、
Query の実装に書けば、差し替える相手のいないポートの interface だけが残る。

### 案 C: 型・門番・SQL を関数 1 本にまとめる（採用）

- **手続きが消える。** ポートの interface・ユースケース・偽物を使うテスト・ルートでの配線が要らなくなる。
- **確かめる場所が 1 つになる。** 読み取りの誤りが出る SQL と門番を、本物の D1 で一緒に確かめる。
- **判定は書き写さない。** 事務局かどうかの門番は 1 か所に集まる。ルートに判定を書く必要もない。

## トレードオフ

| 犠牲・リスク                                                | 対策                                                                                                                                    |
| ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| SQL を書く場所が `app/infra/` と `app/query/` の 2 つになる | 「書き込みは infra、読み取りは query」と言える形にする。infra に残るのは、複数の読み取りで使う部品だけ                                  |
| 移行の途中は、読み取りの書き方が 2 通り混ざる               | 決定 2 の判断を AGENTS.md に載せる。新しく書くものは新しい形にする                                                                      |
| 画面の部品が値を読み込むと、DB のコードがバンドルに入る     | 決定 6。今の部品はどれも `import type` で読み込んでいる                                                                                 |
| 門番のテストのたびに D1 が要る                              | 1 ファイルに 1 件足すだけで済む。D1 はファイルごとに 1 回しか起動しない                                                                 |
| 関数を偽物に差し替えられない                                | 素通しの読み取りには差し替えて試す判断が無い。判断が要るものは決定 2 のとおりユースケースを残し、そちらは今までどおりポートで差し替える |

## 試した結果（事務局のダッシュボード）

4 本を移した前後の行数（2026-10-16）。「本体」は型・SQL・門番・ユースケース、「テスト」は D1 のテストと単体テスト。

| 読み取り                     | 前: 本体 / テスト / ファイル | 後: 本体 / テスト / ファイル |
| ---------------------------- | ---------------------------- | ---------------------------- |
| 今日の予約状況               | 144 / 255 / 5                | 113 / 197 / 2                |
| 承認待ちの予約               | 131 / 268 / 5                | 113 / 245 / 3                |
| 団体からの未読メッセージ     | 210 / 476 / 5                | 181 / 416 / 2                |
| 承認待ちの団体（団体の検索） | 200 / 154 / 4                | 123 / 84 / 2                 |
| 事務局かどうかの門番         | ―                            | 14 / ― / 1                   |
| 合計                         | 685 / 1,153 / 19             | 544 / 942 / 10               |

- 本体は約 2 割、テストも約 2 割減り、ファイルは 19 から 10 になった。ルート 2 つ（ダッシュボードと団体の管理）の配線も 13 行減った。
- 残った行の大半は SQL と D1 のテストで、読み取りの中身そのものである。減ったのは、ポートの interface・ユースケース・偽物を使うテスト・配線という手続きだけだった。
- テストは、門番が止めることを 5 件、D1 のテストに足したうえで減った。団体の検索は、これまで偽物を使うテストでしか門番を確かめていなかった。
- ダッシュボードの「承認待ちの団体」は、これまでユースケース経由で状態ごとの件数も数えていた（画面は使っていなかった）。一覧だけを読む関数を呼ぶようにしたので、事務局がダッシュボードを開くたびの問い合わせが 1 つ減った。
- `pnpm run build` のあと、ブラウザ向けのバンドル（`build/client`）に SQL の文字列が入っていないことを確かめた（決定 6）。

## 移した結果（残りの 6 本）

決定 2 に当てはまる残りの読み取りのうち 6 本を移した前後の行数（2026-10-16）。数え方は上の表と同じ。

| 読み取り       | 前: 本体 / テスト / ファイル | 後: 本体 / テスト / ファイル |
| -------------- | ---------------------------- | ---------------------------- |
| 施設の管理一覧 | 128 / 55 / 4                 | 80 / 82 / 2                  |
| 操作履歴の検索 | 299 / 589 / 5                | 266 / 515 / 2                |
| 事務局の管理   | 126 / 124 / 4                | 93 / 116 / 2                 |
| 自分宛ての招待 | 88 / 204 / 5                 | 70 / 163 / 2                 |
| 団体側の未読   | 301 / 484 / 5                | 293 / 430 / 2                |
| 所属団体の一覧 | 154 / 129 / 4                | 131 / 58 / 2                 |
| 合計           | 1,096 / 1,585 / 27           | 933 / 1,364 / 12             |

- 本体は約 15%、テストは約 14% 減り、ファイルは 27 から 12 になった。団体側の未読の「後」には、ドメインへ移した `GroupUnreadEventType`（15 行）を含めている。
- 団体側の未読と所属団体の一覧は決定 8 に当たり、ポートの interface と `create<出口>Query` が残るので、減り方が小さい。
- 施設の管理一覧はテストが増えた。これまで偽物を使うテストしかなく、並び順と「カレンダーが設定済みか」を本物の D1 で確かめていなかった。
- 事務局の管理画面で期限切れの招待を除く判定を、ユースケースの JavaScript から SQL の条件に移し、境目（期限がちょうど今の時刻）を D1 のテストで確かめるようにした。

## 残っていること

- **素通しのまま残っている読み取り。** `list-facilities-for-calendar-subscription` は決定 2 に当てはまるが、
  団体の予約カレンダー（ADR-013）で購読ページの読み取りを作り直すときに、あわせて移す。
- **所属で判定する読み取り。** 門番が Repository を読む読み取り（団体のメンバーだけが見られる一覧など）を、関数 1 本にしてよいかは決めていない。
  門番が返すエラー（`GroupError` など）と `QueryError` を、ルートでどう扱うかを先に決める必要がある。
- **予約の行の型と JOIN の重なり。** 団体・施設・日時の 6 項目は、`app/query/_shared/reservation-with-names.ts` の型（`ReservationWithNames`）と
  列（`reservationWithNamesColumns`）にまとめた（2026-10-16）。6 項目の一部しか持たない型（予約の詳細・空き状況など）と、
  団体と施設の JOIN（1 行ずつで、まとめても行は減らない）は、そのまま残している。
