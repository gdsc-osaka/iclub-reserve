# ADR-007: E2E テストは UC ごとに、ビルド済みのアプリを手元の Workers で動かして確かめる

## ステータス

提案 (2026-09-24)

実装済みの UC に E2E テストを入れるにあたって、何をどこまで・どう確かめるかを決めた。
この ADR と同じ PR で、土台 (設定・ヘルパー・CI) と見本のテスト (UC-020・UC-002・UC-006) を入れる。

## コンテキスト

- 単体テスト (Vitest、80 ファイル・1058 件) は、ユースケースの判定の分岐をほぼ網羅している
  (例: `change-reservation-status.test.ts` は 23 件)。一方で、画面・ルート・ミドルウェア・DB が
  つながって動くことを確かめるテストは無かった。
- RDRA の UC を実装に合わせて見直し (UC-032〜036 の追加)、実装済みで画面のある UC が 21 件そろった。
  UC を単位にすれば、E2E の期待値を RDRA から取れる。
- ログインは認証コード (メール) とパスキーの 2 通りで、どちらも E2E からそのままでは扱いにくい。
- 手元で試したところ、開発サーバー (`pnpm run dev`) では初めて開く画面で依存の最適化が走り、
  画面が勝手に読み込み直されて操作が失敗した。React の読み込み (hydration) が終わる前に
  ボタンを押すと、何も起きないことも分かった。

## 決定

### 1. E2E で確かめるのは「主な流れ」「権限の境目」「代表的な失敗 1 つ」だけにする

| 確かめること                                                       | E2E | 単体テスト |
| ------------------------------------------------------------------ | :-: | :--------: |
| 画面の操作が、ルート・ユースケース・DB を通って画面に出る (正常系) |  ○  |            |
| 誰がその画面を開けるか・操作できるか                               |  ○  |  ○ (判定)  |
| 失敗したとき、利用者にエラーが見える (UC ごとに代表 1 つ)          |  ○  |            |
| どの条件で失敗するか (COND の全分岐・境界値)                       |     |     ○      |
| エラーの文言と status の対応                                       |     |     ○      |
| メールの配送 (Queue・Cron・SMTP)                                   |     |     ○      |

同じ分岐を E2E でもなぞると、遅くて壊れやすいテストが増え、変更のたびに両方を直すことになる。
分岐を足したくなったら、まずユースケースの単体テストに書けないかを考える。

### 2. シナリオは「UC × 操作」で切る

1 つの UC に複数の操作がある (UC-011 は招待・招待の取り消し・メンバーの削除) ので、操作ごとに 1 本にする。
対象は実装済みで画面のある 21 UC、44 本を見込む。一覧は RDRA のコンテキストごとにフォルダを分けて置く。

- ファイル: `e2e/<RDRA のコンテキスト>/uc-<番号>-<内容>.spec.ts` (1 ファイル 1 UC)
- テスト: `test.describe("UC-003 仮予約を取り消す", { tag: "@UC-003" }, ...)` の中に、操作ごとの `test` を書く
- UC とテストの対応はタグで取る。別の表は持たない。`pnpm exec playwright test --grep @UC-003` で UC ごとに動かせる

### 3. Playwright で、ビルド済みのアプリを手元の Workers で動かす

`pnpm run test:e2e` は、`react-router build` の後に Playwright を起動する。
Playwright は `playwright.config.ts` の webServer で `e2e/prepare.ts` を実行してから、
`vite preview` (miniflare の上でビルド済みの Worker を動かす) をポート 4173 で起動する。

- 開発サーバーは使わない (コンテキストを参照)。
- Cloudflare のプレビュー環境も使わない。D1 とメールのキューを `develop` と共有しているので、
  ほかの PR と同時に動くとデータがぶつかる。認証コードも Discord に流れる。
- `wrangler.jsonc` に E2E 用の環境は足さない。トップレベル (`APP_ENV = "local"`) をそのまま使う。
- ポートを開発サーバー (5173) と分けたので、開発サーバーを止めずに E2E を動かせる。
- 同じテストを 5 種類のブラウザで動かす (`playwright.config.ts` の projects、2026-09-24 追加)。
  パソコンの Chromium・Firefox・WebKit と、スマホの Chrome (Pixel 7)・Safari (iPhone 15)。
  スマホの幅ではナビゲーションがボトムバーに、空き状況が日ごとの一覧に変わるので、
  操作が変わるテストは Playwright の `isMobile` を見て分ける (アカウントのメニューは `e2e/support/account-menu.ts`)。
  確かめたいことは同じにし、画面ごとに別のテストを書き足すことはしない。

### 4. E2E のアプリの設定は `build/server/.dev.vars` に E2E 用の値を書いて渡す

`vite preview` はビルドのときに写された `build/server/.dev.vars` を読む。`e2e/prepare.ts` がここを
E2E 用の値 (`e2e/support/e2e-env.ts`) で上書きする。

- 手元の `.dev.vars` が無くても、何が書いてあっても、E2E は同じ設定で動く。CI で `.dev.vars` を作る必要もない。
- SMTP の認証情報を空にするので、テスト中のメールは実際には送られず、ターミナルに出るだけになる。
- Better Auth の秘密鍵は E2E 専用の固定値にする。手元の E2E のアプリでしか使わないのでリポジトリに書く。
  テスト側でも同じ値で Cookie に署名する (決定 6)。

### 5. DB は E2E 専用のフォルダに毎回作り直し、シードは開発用と共有する

- `@cloudflare/vite-plugin` の `persistState` を、環境変数 `E2E_PERSIST_TO` があるときだけ
  `.wrangler/e2e-state` に向ける (`vite.config.ts`)。開発用の `.wrangler/state` は壊さない。
- `e2e/prepare.ts` がこのフォルダを消し、`wrangler d1 migrations apply --local --persist-to` でマイグレーションを当て、
  開発用と同じシード (`scripts/seed/insert-seed-data.ts`) を入れる。
- シードの利用者には立場の名前を付けた (`seedPersonas`: 事務局・団体の管理者・一般メンバー・未所属・承認待ちの団体の管理者)。
  テストは `personas.staff` のように立場で人を選ぶ。立場を変えるときは `e2e/` も確かめる。
- テストが書き換えるもの (団体・施設・予約など) は、各テストの最初に DB へ直接入れる (`e2e/support/factories.ts`)。
  名前と ID にテストごとの印を付けるので、テストの順番に左右されない。動いているアプリの DB に外から書いても、すぐ画面に出る。
- 状態や役割は `~/domain` の定数を使い、文字列を書き写さない。
- 日時は「来週の水曜 10:00」のようにテストを動かした日から決める (`e2e/support/dates.ts`)。サーバーの時計は止められない。

### 6. ログインは、ログインそのものを確かめるテストだけ画面で行う

- ふだんは Better Auth の `testUtils` (`better-auth/plugins` に同梱) で DB にセッションを作り、
  署名済みの Cookie をブラウザに渡す (`signInAs`)。画面を通らないので速く、ログインと関係のない所で落ちない。
- UC-019・UC-020 は画面で認証コードを入れる。認証コードは DB の `verification` の行
  (`sign-in-otp-<メールアドレス>`、値は `<認証コード>:<試した回数>`) から読む。
  メールアドレスの変更 (UC-023) の認証コードも、同じように使い道ごとの名前の行から読む (`otpIdentifier`)。
  Better Auth の `storeOTP` を平文 (既定) 以外に変えると読めなくなるので、そのときはこの方法を見直す。
- パスキー (UC-020・UC-021) は Chromium の仮想認証器 (CDP の WebAuthn) で扱う。rpID は `localhost` になる。
- 仮想の WebAuthn はすべてのテストで有効にし、認証器は置かない (fixture の `webAuthn`)。アプリは「この端末で
  パスキーを作れるか」でログイン後の行き先を変えるが、その答えは本物の端末に左右される (Windows Hello がある
  Windows では作れる、CI の Linux では作れない)。仮想の環境ではブラウザが仮想の認証器だけを見るので、どの OS でも
  「作れない」に揃う。パスキーを使うテストは `webAuthn` に仮想の認証器を足す (`e2e/support/passkey.ts`)。
- 仮想の認証器は Chromium の CDP でしか作れない。Firefox・WebKit では、ブラウザの「作れるか」「自動入力に対応しているか」の
  答えを「いいえ」に差し替えて同じ状態に揃え (`hidePlatformAuthenticator`)、`webAuthn` を使うテストは飛ばす (結果には skipped と出る)。
  パスキーの登録・ログインは Chromium (パソコンとスマホ) で確かめる。
- 仮想の認証器は人の操作を待たずに答えるので、ログイン画面を開いただけで、パスキーの自動入力 (条件付き UI) で
  ログインが終わることがある。「パスキーでログイン」のボタンを確かめるテストは、自動入力に対応していない
  ブラウザとして画面を開く (`disablePasskeyAutofill`)。

### 7. 画面は、読み込みが終わってから操作する

`app/root.tsx` が、ブラウザで React の読み込みが終わったら `<html data-hydrated="true">` を付ける。
テストは画面を開くときに `openPage` (`e2e/support/page.ts`) を使い、この印を待ってから操作する。

- 要素はロールとラベルで探す (`getByRole`・`getByLabel`)。CSS のクラスや DOM の位置に頼らない。
- 非同期の結果は、次に出る画面の要素を合図に待つ。DB を合図にしない (前の結果が残っていることがある)。

### 8. 通知は `mail_outbox` に積まれたことまでを確かめる

宛先と件名、本文の予約 ID で見分ける (`e2e/support/mail.ts`)。送信済みかどうか (`status`) は見ない。
E2E のアプリでも Queue が動くので、すぐに `sent` に変わることがある。

### 9. CI では独立したジョブにし、安定するまでは必須にしない

`ci.yml` の `E2E` ジョブで、ブラウザを入れてビルドし、テストを動かす。落ちたら trace と画面の写真を成果物に残す。
ブラウザごとに別のジョブ (`E2E (chromium)` など 5 つ) にして並行して動かし、1 つが落ちてもほかは最後まで動かす。
テストは 1 つずつ順に動かし、落ちたテストはやり直さない (たまに落ちるテストはやり直しで隠さずに直す)。

### 10. UC を実装・変更する PR に、その UC の E2E を含める

- UC を実装して `docs/implementation-status.md` で ✅ にする PR に、その UC の E2E を入れる。
- RDRA の UC の記述が変わったら、その UC のタグのテストを見直す。

## 理由

- **開発サーバーではなくビルドを使う**: 依存の最適化による読み込み直しは、テストの中身と関係なく起きる。
  ビルドなら起きず、本番と同じコードを確かめられる。ビルドは 10 秒ほどで済む。
- **プレビュー環境を使わない**: データを共有しているうえ、認証コードを受け取れない。
- **前提を DB に直接入れる**: 前提を画面から作ると遅く、確かめたい操作と関係のない画面の変更でテストが落ちる。
- **シードを開発用と共有する**: E2E のためだけの固定データを別に持つと、2 か所を保つことになる。
  立場に名前を付けておけば、開発の都合でシードを変えても E2E に響く所が分かる。

## トレードオフ

- アプリに E2E のためだけのコード (`data-hydrated` の印) が入る。
- テスト側の Better Auth の設定は、本体の設定と別に持つ。本体の `user` の列を変えたら合わせる必要がある。
- 認証コードの読み取りは Better Auth の保存の形に頼っている (決定 6)。
- 前提を DB に直接入れるので、テーブルの形を変えるとヘルパー (`e2e/support/factories.ts`) も直す必要がある。
- E2E を動かすたびにビルドする。ビルド済みなら `pnpm exec playwright test` だけでもよい。
