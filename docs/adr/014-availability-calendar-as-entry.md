# ADR-014: 空き状況カレンダーを予約の申請の入口にし、並べる日数は幅で変え、開いているものを URL に置く

## ステータス

提案 (2026-10-26)

Issue #199 を受けて決める。作業は 3 つの PR に分ける（決定 1）。この ADR には 1 つ目の PR（カレンダーの表示・予約の内容と仮の枠を出す欄・ナビの入口）で決めたことを書く。2 つ目以降で申請・変更をカレンダーの欄の中へ移すときに、この ADR に書き足す。

## コンテキスト

予約を作るまでの流れが分かりにくい（#199）。

- **入口が散らばっている。** ダッシュボードの「予約を申請」、空き状況カレンダー（SCR-001）の「仮予約を申請」と空き枠があり、ナビには無い。文言も「予約を申請」「仮予約を申請」「仮予約の申請」と揃っていない。
- **同じことを 2 回選ぶ。** 空き状況カレンダーで施設・日付・時刻を選んでから、予約申請フォーム（SCR-002）のタイムラインで同じことを選び直す。どちらも「その日・その施設の予約を見て時間帯を選ぶ」画面で、意味が重なっている。確認も、空き枠の吹き出しとフォームの確認のダイアログで 2 回ある。
- **PC とスマホで操作が違う。** PC は週の表で、空き枠から時刻まで選べる。スマホは日ごとの一覧で、日付の「＋」からフォームへ移ってから時刻を選ぶ。
- **時間帯が意図とずれる。** 空き枠は 1 時間単位なのに、押すとフォームには「13:00〜13:30」が入る。

目指すのは、Google カレンダーのように、カレンダーで時間を選び、その場の欄で申請する形である。

## 決定

### 1. 3 つの PR に分ける

1. カレンダーの表示（7・5・3 日）、予約の内容と仮の枠を出す欄、ナビの入口。申請はまだ今のフォームへ移る（この ADR）。
2. 申請をカレンダーの欄の中で行う。団体・人数・備考の入力と送信、時刻の手入力、PC のなぞり選択、仮の枠の丸での伸び縮み。`/reservations/new` はカレンダーへ転送する。
3. 予約の変更もカレンダーの欄の中で行う。`/reservations/:reservationId/edit` もカレンダーへ転送する。

### 2. 並べる日数はカレンダーの枠の幅で決め、CSS だけで切り替える

| カレンダーの枠の幅 | 並べる日数 |
| ------------------ | ---------: |
| 52rem 以上         |       7 日 |
| 36rem 以上         |       5 日 |
| それ未満           |       3 日 |

- 画面の幅（メディアクエリ）ではなく、カレンダーの枠の幅（コンテナクエリ）で決める。サイドバーや欄の開閉で、画面の幅が同じでも枠の幅が変わるため。
- JavaScript では幅を測らない。サーバーで描いた最初の画面と、読み込みが終わった後の画面が食い違い、ちらつくため（サイドバーとボトムバーの切り替えと同じ考え方）。
- 52rem は、今の週の表が 7 日を並べるのに取っていた最低の幅である。

### 3. 7 日の表示は日曜〜土曜で固定し、5 日・3 日の表示は 1 日ずつ動く

- 7 日の表示は「週」として読まれる。紙のカレンダーも、この画面の「今週」も、日曜から土曜の区切りでできている。途中の曜日から始まる 7 日を出すと、どこからどこまでが今週なのかを読み直す手間が増える。週全体がもう見えているので、1 日ずらしても新しく見える日は 1 日だけで、利点も小さい。
- 5 日・3 日の表示は、横に送って 1 日ずつ動けるようにする。
- 両方を、横に流れる 1 本の日の列で作り、止まる位置だけを変える。止まる位置は CSS の `scroll-snap` で決め、7 日の表示では日曜の列だけ、5 日・3 日の表示ではすべての列で止める。`scroll-snap-stop: always` を付けて、勢いよく送っても 1 週・1 日ずつしか進まないようにする。
- 前後へ移るボタンは、並べている日数（7・5・3）ぶん動く。横のホイールとスワイプは、止まる位置に任せる。縦のホイールは時刻のスクロールに使う。
- 幅が変わって日数が変わったときは、先頭に見えていた日を保つ。7 日の表示になるときは、その日を含む週の日曜に合わせる。

### 4. 4 週間ずつ読み、端に近づいたら基準を変えて読み直す

- URL の `date` を基準にし、その日を含む週の前の週から 4 週間（前の週・その週・後の 2 週）を読む。`date` が無ければ今日を基準にする。
- 見えている範囲の外に、並べている日数ぶんの日が残っていない側があれば、先頭に見えている日を新しい基準にして読み直す。URL の `date` は履歴に積まずに書き換え、読み直した後も先頭に見えていた日の位置を保つ。
- 3 週間ではなく 4 週間にしているのは、読み直した直後にもう一度読み直しが起きないようにするため。5 日の表示で土曜を基準にしても、右に 1 画面ぶん以上の日が残る。
- 1 施設の 4 週間ぶんの予約は多くても数十件で、通信量は問題にならない。読み取り（`getAvailabilityCalendarUseCase`）は期間を受け取れるので、変えるのはローダーが渡す期間だけである。

### 5. 最初に描くときは、基準より前の日を CSS で隠しておく

スクロールの位置は、サーバーで描いた時点では決められない。基準の日を左端に出したくても、そのまま描くと読み込みが終わってから横へ飛ぶ。

そこで最初は、基準の日（7 日の表示ではその週の日曜）より前の列を CSS で隠しておく。読み込みが終わったら、画面に描かれる前（`useLayoutEffect`）に列を出し、スクロールの位置を合わせる。

### 6. 押せる場所は 30 分ずつにし、予約の帯は列の右に余白を残す

- 1 時間の上半分を押すと毎時 0 分、下半分を押すと 30 分から始まる仮の枠を出す。1 時間の高さは今のまま（3.25rem）にする。
- 仮の枠は 1 時間にする。承認済みの予約か利用できる時間帯の終わり（21:00）に当たって 1 時間取れないときは 30 分にする。承認済みの予約がある時間帯と、過ぎた時間帯からは始められない。
- 予約の帯は、列の右端に余白を残して描く。仮予約どうしは重なってよいので（COND-001）、余白を押せば仮予約の上からでも申請を始められる。
- 30 分の枠は Tab で巡らせない。4 週間ぶんで 672 個になり、キーボードでは画面を抜けられなくなる。キーボードでは、ナビの入口から申請フォームを開いて時刻を選ぶ。2 つ目の PR で、欄に時刻の手入力を置く。

### 7. 欄はカレンダーの隣に並べ、画面に重ねない

- 予約の内容と仮の枠は、PC ではカレンダーの右、スマホではカレンダーの下に出す。画面に重ねるダイアログにはせず、カレンダーと幅（PC）・高さ（スマホ）を分け合う。
- 欄を開いたまま、カレンダーで別の予約や時間を選び直せるようにするため。重ねると、選んだ枠が欄の下に隠れる。
- 下から出す引き出し（shadcn/ui の Drawer）は使わない。元にしている vaul は、作者が README で保守をやめたと書いている。
- PC で欄を開くとカレンダーの枠が狭まり、7 日から 5 日の表示に変わることがある。選んだ日が見えなくなるときは、見える位置まで送る。

### 8. 開いているもの（予約・仮の枠）は URL に置き、閉じた状態から開くときだけ履歴に積む

- 予約は `?reservation=<予約ID>`、仮の枠は `?draft=YYYY-MM-DDTHH:MM-HH:MM` で表す。そのまま人に送れ、再読み込みしても同じものが開く。
- 閉じた状態から開くときは履歴に積み、戻る操作（スマホの戻るジェスチャーを含む）で閉じられるようにする。開いたまま別のものを選び直すときは積まない。積むと、戻る操作を何度も繰り返さないと画面を離れられない。
- 欄を開く・閉じる・選び直すだけでは、ローダーを走らせない（`shouldRevalidate`）。出すものは手元のデータにある。
- 承認・却下などの操作の後は、今と同じく同じ URL へ戻すので、欄は開いたまま新しい状態で出る。

### 9. ナビの入口は、申請できない人にも出す

- PC はサイドバーの最上部、スマホはボトムバーの中央に置く。文言はダッシュボードと同じく、団体は「予約を申請」、事務局は「予約を作成」とする。
- 申請できない人（承認待ちの団体にしか所属していない・団体に所属していない）にも出す。押した先の申請フォームが、申請できない理由と、団体の確認・登録への導線を出す。入口を隠すと、なぜ申請できないのかが分からないまま画面を探し回ることになる（空き状況の画面の案内と同じ考え方）。外枠の loader に所属の読み取りを足さずに済む。
- ボトムバーは 5 つのままにする（項目 4 つ + その他 → 項目 3 つ + 入口 + その他）。押し間違えずに並べられるのは、幅 320px の端末で 5 つまでのため。団体のボトムバーでは「所属団体」、事務局のボトムバーでは「予約」（自団体の予約の一覧）を「その他」へ移す。事務局は承認の一覧を、団体は自団体の予約の一覧を、よく開くため。
- 1 つ目の PR では、入口は今の申請フォーム（`/reservations/new`）を開く。2 つ目の PR で、カレンダーの欄を開くように変える。

## 採らなかった案

- **7 日の表示も 1 日ずつ動かす。** 決定 3 のとおり、週の区切りが崩れて読みにくくなる。
- **画面の幅（メディアクエリ）で日数を決める。** サイドバーや欄の開閉で枠の幅が変わっても、日数が追従しない。
- **今のまま、週ごとに画面を切り替える。** 横に送る操作と合わず、3 日の表示で 1 日ずつ動けない。
- **ナビの入口を、申請できない人には出さない。** 決定 9 のとおり。

## 影響

- PC の週の表（`AvailabilityWeekGrid`）とスマホの日ごとの一覧（`AvailabilityWeekAgenda`）を、1 つのカレンダーに置き換える。スマホでも時刻を選んで申請へ進めるようになる。
- 予約と空き枠の吹き出し（Popover）はやめ、欄に出す。カレンダーの見出しの「仮予約を申請」は、ナビの入口と重なるので消す。
- 空き状況の読み取りに、見ている人がその予約の内容を変更できるか（`canEdit`）を足す。判定はドメインの `canChangeReservationContent` に任せる。
- 予約申請フォーム（`/reservations/new`）は、終了時刻（`end`）も受け取る。
- UC-001・UC-006・UC-008 の E2E を書き直す。
- 横のホイールでの送りと、スナップの止まり方は、ブラウザ（Chromium・Firefox・WebKit）と入力の機器（マウス・トラックパッド・指）で違いが出る。E2E では確かめられないので、手で確かめる。

## 残っていること

- 2 つ目・3 つ目の PR（決定 1）。
- 施設を切り替えると、URL の `date`（読み直しの基準）の位置へ戻る。横に送った後の先頭の日までは持ち越さない。
- 30 分の枠をキーボードで選ぶ方法（矢印キーで枠を移るなど）。
