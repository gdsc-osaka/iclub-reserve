# ADR-013: 自団体の予約のカレンダーを、所属ごとの秘密の URL で iCal として配信する

## ステータス

提案 (2026-10-26)

ADR-008（Google Calendar との予定同期）は施設ごとのカレンダーについての決定で、本 ADR はそれを変えない。

## コンテキスト

団体のメンバーが、自団体の予約だけを、ふだん使っているカレンダーアプリ（Google カレンダー・Apple カレンダー・Outlook など）で確かめられるようにする（#195・REQ-050・UC-039）。施設ごとのカレンダーの購読 URL（REQ-030）は、団体のメンバーにとっては他団体の予約が混ざるだけなので、事務局にだけ出すことにした。要件は `rdra/contexts/calendar-integration.md` の COND-029 にまとめてある。設計にあたっての制約は次のとおり。

1. **カレンダーアプリはログインできない。**
   購読したカレンダーは、アプリ（Google カレンダーならそのサーバー）が URL を定期的に読みに来る。Cookie もログインの画面も通らないので、URL そのものを鍵にするしかない。
2. **Google Calendar を団体ごとに作る方法は運用に合わない。**
   ADR-008 と同じように、共有の Google アカウントで団体ごとにカレンダーを作り、Service Account に共有して ID を登録すると、団体が増えるたびに事務局の手間がかかる。自団体の予約は団体のメンバーだけが見る情報なので、施設のカレンダーのように一般公開もできない。一人ずつ Google アカウントに共有するには、学内のメールアドレスが Google アカウントである必要がある。Service Account が自分でカレンダーを作る方法もあるが、権限を `calendar.events` から `calendar` に広げることになり、持ち主が Service Account になって事務局が引き継げない（REQ-026 の考え方と合わない）。
3. **URL が漏れたときと、メンバーが抜けたときに止められること。**
   URL で読める項目には備考を含む（COND-029 の (3)）。漏れたら本人が止められ、団体を抜けた人の URL は自動で止まる必要がある。
4. **Cloudflare Workers の上限。**
   1 回の実行あたりのサブリクエスト（D1 の問い合わせを含む）は Free プランで 50 件まで（ADR-008 のコンテキスト 3）。カレンダーアプリは購読している人数分、1 時間〜1 日おきに読みに来る。

## 決定

**団体の所属（`group_member`）ごとに推測できない乱数のトークンを 1 つ持たせ、`/calendar-feeds/<トークン>.ics` に来た要求に、その時点の予約から組み立てた iCal（RFC 5545）を返す。Google Calendar には書き込まない。**

### 1. 全体像

```text
[団体管理画面（SCR-007）] メンバー本人が「発行」「作り直し」
   │
   └─ group_calendar_feed に INSERT / トークンを UPDATE（所属ごとに 1 行）

[カレンダーアプリ] GET /calendar-feeds/<トークン>.ics（アプリが決める間隔で）
   │
   ├─ トークン → 購読の行 → 所属 → 団体 → 予約 を 1 本の関数でたどる
   ├─ 見つかった: 仮予約・承認済み、終了が 90 日前より後の予約を iCal にして 200
   ├─ 見つからない（存在しない・作り直した・抜けた）: 予定 0 件の「無効になったカレンダー」を 200
   └─ D1 の失敗: エラーの応答（0 件のカレンダーは返さない）

[メンバーの削除（UC-011）・アカウントの削除]
   └─ group_member の行が消える → 外部キーの ON DELETE CASCADE で購読の行も消える
```

配信のたびに予約から組み立てるので、ADR-008 のような同期タスク・再試行・日次の突き合わせは要らない。カレンダーアプリが読み直した時点で、必ず予約の今の状態になる。

### 2. テーブル（`group_calendar_feed`）

`app/db/schema/calendar.ts` に置く。

```ts
export const groupCalendarFeedTable = sqliteTable("group_calendar_feed", {
  id: text("id")
    .primaryKey()
    .$defaultFn(() => createId()),
  membershipId: text("membership_id")
    .notNull()
    .unique()
    .references(() => groupMemberTable.id, { onDelete: "cascade" }),
  token: text("token").notNull().unique(),
  createdAt: integer("created_at", { mode: "timestamp_ms" })
    .notNull()
    .$defaultFn(() => new Date()),
  updatedAt: integer("updated_at", { mode: "timestamp_ms" })
    .notNull()
    .$defaultFn(() => new Date()),
});
```

- **利用者と団体ではなく、所属の行に結び付ける。**
  メンバーの削除（自分を外す場合を含む）は `group_member` の行を消す（`app/infra/membership/membership-repo.ts`）。購読の行は外部キーの `ON DELETE CASCADE` で一緒に消えるので、抜け方ごとに「購読も消す」と書かなくてよい。抜け方が今後増えても書き忘れが起きない。アカウントの削除も、`user` → `group_member` の cascade を通って消える。
  D1 は外部キーの制約を既定で守る（`group_member` → `group`、`reservation_read` → `user` の cascade も同じ前提で動いている）。この前提は D1 のテストで確かめる（決定 9）。
- **入り直しても前の URL は生き返らない。**
  入り直すと所属の行が新しくなるので、購読の行も新しくなる。利用者と団体の組に結び付けて、取得のたびに所属を確かめるだけの作りだと、入り直した時点で古い URL が生き返る。抜けている間に URL が人に渡っていた場合を考えると、生き返らないほうが安全である。
- **`membership_id` を一意にする。**
  所属ごとに 1 つ（COND-029 の (1)）を DB でも守り、発行と作り直しを `INSERT ... ON CONFLICT (membership_id)` で書けるようにする（決定 6）。

### 3. トークン

- **作り方**: `crypto.getRandomValues` で 32 バイト（256 ビット）を作り、base64url（パディングなし、43 文字）にする。総当たりで当てることはできない。
- **ハッシュにせず、そのまま持つ。**
  本人が団体管理画面で何度でも URL を表示できるようにするためである（COND-029 の (1)）。ハッシュにすると、発行したときに一度だけ見せ、見失ったら作り直すしかなくなる。
  ハッシュにする目的は「データベースが漏れても、鍵として使えない」ことだが、この URL で読めるのは同じデータベースにある予約だけなので、データベースが漏れた時点で読まれる内容は変わらない。残る違いは、漏れた後に入る予約まで読み続けられることで、これは作り直しで止める（トレードオフ）。
- **URL のパスに入れる（クエリ文字列にしない）。**
  `.ics` で終わる URL にしておくと、拡張子でカレンダーだと判断するアプリにも読ませられる。
- **アプリのログにトークンを出さない。**
  ログに購読を書くときは、トークンではなく行の `id` を使う。Workers Logs には要求の URL が残るので、そこにはトークンが載る（トレードオフ）。

### 4. 配信のルート

- `app/routes/calendar-feeds/$fileName/route.ts` に loader だけのリソースルートを置き、`app/routes.ts` に `route("calendar-feeds/:fileName", ...)` を足す。React Router は `:token.ics` のようにセグメントの一部だけを動的にできないので、`:fileName` で受けて `.ics` を取り除く。`.ics` で終わらなければ普通の 404 にする。
- `app/lib/auth/auth-redirect.ts` の `PUBLIC_PATH_PREFIXES` に `/calendar-feeds/` を足し、ログインを免除する。接頭辞の下は、まだ無いパスも含めてログイン不要になるので、このフォルダにはこのルートしか置かない。
- 応答のヘッダー:
  - `Content-Type: text/calendar; charset=utf-8`
  - `Cache-Control: private, max-age=300`（途中の共有キャッシュに URL ごと残させない）
  - `X-Robots-Tag: noindex`
- **見つからないときは、予定 0 件のカレンダーを 200 で返す（COND-029 の (6)）。**
  カレンダーアプリの中には、取得に失敗すると前に取れた予定を表示し続けるものがある。404 を返すと、漏れた先や抜けた人の手元に備考つきの予定が残るおそれがある。0 件のカレンダーを正常に返せば、次に読み直したときに手元の予定が消える。カレンダーの名前は「無効になったカレンダー（i-Club）」にし、作り直した本人が古い購読に気づけるようにする。
  存在しないトークン・作り直す前のトークン・抜けた人のトークンは、どれも同じ応答になるので、URL が実在したかは漏れない。古い URL は、購読をやめるまでアプリが読みに来続けるので、見つからなかったことはログに残さない（残すと、毎回の読み直しがログを埋める）。総当たりはトークンの長さで防ぐ。
- **読み取りに失敗したときは、0 件のカレンダーを返さない。**
  一時的な D1 の失敗で利用者の手元の予定を消さないためである。`throw queryErrorResponse(...)` でエラーの応答を返し、ログを残す（ADR-004）。アプリはエラーの応答なら前の予定を残して、次の機会に読み直す。`ErrorContext` の `userId` には、ログインしていない要求であることを表す固定の値を入れる（トークンは入れない）。
- 予約詳細へのリンクと、画面に出す URL の組み立てには、メールのリンクと同じ `resolveAppBaseUrl` を使う。

### 5. 配信の読み取りは、ADR-012 の素通しの読み取りにする

配信の読み取りは `app/query/calendar/group-calendar-feed.ts` の関数 `findGroupCalendarFeed(db, { token, since })` 1 本にし、ポート・`app/infra/` の実装・ユースケースは作らない。返り値は `ResultAsync<GroupCalendarFeed | null, QueryError>` で、見つからなければ `null` を返す。

ADR-012 の 3 つの条件に照らすと、次のとおりである。

| 条件                             | 配信の読み取り                                                                                     |
| -------------------------------- | -------------------------------------------------------------------------------------------------- |
| 見る人の判定が門番 1 つで済む    | 判定そのものが無い。トークンが「誰の分を読むか」を決め、購読 → 所属 → 予約を結合でたどるだけである |
| 見る人によって返す形が変わらない | 変わらない。読めるかどうかと、読める範囲は COND-029 の (2)(3) で決まっている                       |
| 読むのと同時に書き込まない       | 書かない。最後に読まれた日時は記録しない（決定 8）                                                 |

AGENTS.md は「所属で判定する」読み取りを素通しから外している。これは、ログインした人の所属を読んでから、見せるかどうか・何を見せるかを決める読み取り（`get-reservation` など）を指す。配信では、所属は鍵から予約へたどる結合の条件であり、読んだ後に分岐する判断は無い。偽物のポートで試す判断が無いので、ユースケースを置く理由が無い。

画面に合わせた詰め替え（予約 → iCal の予定）は純粋な `to*` 関数に分ける（ADR-012 決定 3）。

- `app/lib/ical.ts`: iCal の文字列を組み立てる汎用の道具。行末は CRLF、テキストの `\`・`;`・`,`・改行を逃がし、75 オクテットで折り返す。日本語は 1 文字 3 バイトなので、UTF-8 の文字の途中で切らない。時刻は UTC（`YYYYMMDDTHHMMSSZ`）で書き、`VTIMEZONE` は持たない。
- `app/domain/calendar/group-calendar-feed.ts`: 予約から予定への詰め替え（`toGroupCalendarEvents`）と、業務の数字（過去に遡る日数 90・仮予約の接頭辞 `[仮予約] `）の定数。
  - カレンダー: `X-WR-CALNAME`（`<団体名> の予約（i-Club）`）・`X-WR-TIMEZONE:Asia/Tokyo`・`REFRESH-INTERVAL;VALUE=DURATION:PT1H`・`X-PUBLISHED-TTL:PT1H`
  - 予定: `UID`（`<予約ID>@iclub-reserve`。変えない）・`DTSTAMP` と `LAST-MODIFIED`（予約の `updated_at`）・`DTSTART`・`DTEND`・`SUMMARY`（施設名。仮予約は接頭辞付き）・`LOCATION`（施設名）・`DESCRIPTION`（使用人数・備考・予約詳細のリンク）・`URL`（予約詳細）・`STATUS`（仮予約は `TENTATIVE`、承認済みは `CONFIRMED`）
  - 取り消し・却下・キャンセルで終わった予約は、`STATUS:CANCELLED` で載せずに、そもそも載せない。購読したカレンダーは毎回まるごと置き換わるので、載せなければ消える。

ライブラリは足さない（AGENTS.md の「不要な依存を足さない」）。使う機能は上の数個だけで、単体テストで固められる。

### 6. 発行と作り直しは、ユースケースにする

書き込みなので、ADR-001 の形（Repository のポートとユースケース）で書く。

| ユースケース                                              | 中身                                                                                                 |
| --------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `app/usecases/calendar/issue-group-calendar-feed.ts`      | 所属を確かめ、無ければ作る（`INSERT ... ON CONFLICT (membership_id) DO NOTHING`）。二度押しても 1 つ |
| `app/usecases/calendar/regenerate-group-calendar-feed.ts` | 所属を確かめ、トークンを置き換える（`... DO UPDATE SET token = ..., updated_at = ...`）              |

- **門番**: 操作する人の所属を引き、無ければ止める。事務局でない人には `NotVisible`（団体の存在を伏せる。COND-011）、事務局には `Forbidden` を返す（団体は見られるが、所属していない団体の URL は発行できない。COND-029 の (1)）。`groupPermissions` の表は使わない。表は「事務局は団体の役割をすべて含む」という前提で作られているが（`group-authorization.test.ts`）、この操作だけは事務局にも許さないためである。所属を返す門番なので `resolve*` の名前にし、2 つのユースケースで共有するので `app/usecases/group/_shared/` に置く。
- **エラー**: 団体の操作なので `GroupError` を返し、ルートは今までどおり `groupActionErrors` を呼ぶ（ADR-004）。
- **トークンの生成**: ユースケースの依存として関数を受け取り、テストでは決まった値を返す偽物を渡す。
- **操作履歴に書かない**（COND-029 の (7)）。本人の設定の変更で、団体の業務データを変えないため。

団体管理画面の loader（`get-group-management`）は、見る人が所属していれば自分の購読の行を読み、トークンを返す。見る人によって返す形が変わるので、このユースケースの中で Repository のポートを通して読む（ADR-012 決定 2）。URL の組み立て（`https://`・`webcal://`・Google カレンダーへの追加のリンク）はルートで行う。Google カレンダーへの追加は `https://calendar.google.com/calendar/render?cid=<webcal の URL を encodeURIComponent したもの>` を使う。

### 7. 施設のカレンダーの画面は事務局だけにする

`/calendars`（SCR-010）は、ほかの事務局の画面にそろえて `/staff/calendars` に移し、ナビの項目を `staffNavItems` に移す。まだ公開していないので、古いパスからの転送は置かない。loader は `ensureStaff` で止める。

### 8. 最後に読まれた日時は記録しない

漏れた URL が実際に使われたかを後から確かめるには、読まれた日時を残す手がある。しかし、読むたびに D1 へ書き込むことになり、配信の読み取りが素通しでなくなる。カレンダーアプリは購読している人数分、定期的に読みに来るので、書き込みの量も増える。漏れたと思ったら作り直せばよく、使われたかどうかは判断に要らないので、記録しない。

### 9. テスト

AGENTS.md・ADR-007・ADR-012 決定 5 に従う。

| テスト                                                   | 確かめること                                                                                                                       |
| -------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `app/lib/ical.test.ts`                                   | 逃がす文字、75 オクテットでの折り返し（日本語の文字の途中で切らない）、CRLF                                                        |
| `app/domain/calendar/group-calendar-feed.test.ts`        | 仮予約の接頭辞と `STATUS`、説明の組み立て（備考の改行を含む）、0 件のカレンダー                                                    |
| `app/query/calendar/group-calendar-feed-d1.test.ts`      | 存在しないトークンは `null`、他団体の予約と終わった予約を含まない、90 日の境目、所属を消すと `null`、作り直す前のトークンは `null` |
| Repository の D1 テスト                                  | 二度の発行で 1 行、作り直しでトークンが変わる、所属を消すと行も消える（D1 が cascade を守ることの確認）                            |
| 発行・作り直しのユースケースのテスト                     | 所属していれば通る、所属していない人は `NotVisible`、所属していない事務局は `Forbidden`                                            |
| `e2e/calendar-integration/uc-039-*.spec.ts`（`@UC-039`） | 団体管理画面で発行して URL を読むと予約が載っている（主な流れ）、作り直す前の URL は 0 件になる（代表的な失敗）                    |
| `e2e/calendar-integration/uc-018-*.spec.ts`（`@UC-018`） | 事務局でない利用者は施設のカレンダーの画面を開けない（権限の境目）                                                                 |

E2E では、URL を Playwright の `request` で読み、返った iCal の中身を確かめる。Google カレンダーへの追加のリンクは、Google から `localhost` を読めないので、プレビュー環境に出してから Google カレンダーと Apple カレンダーに登録して確かめる。0 件のカレンダーを返したときに手元の予定が消えるかも、そこで確かめる。

### 10. 実装の進め方

1. **要件と本 ADR**（この PR）: RDRA・PRD・change-log・implementation-status の更新と、本 ADR。
2. **配信**: テーブルとマイグレーション、`app/lib/ical.ts`、予約から予定への詰め替え、`findGroupCalendarFeed`、配信のルートとログインの免除。発行の画面が無くても、D1 のテストで動きを確かめられる。
3. **発行と画面**: Repository・発行と作り直しのユースケース、団体管理画面のカード（発行・Google カレンダーへの追加・カレンダーアプリで開く・コピー・作り直しの確認）、`get-group-management` の変更、施設のカレンダーの画面を事務局だけにする変更、E2E、implementation-status の ✅。

## 結果

1 回の配信では、D1 への問い合わせが 1〜2 回（購読と団体の行、予約の一覧）で済み、Google への呼び出しは無い。Free プランのサブリクエストの上限（50 件）に対して十分に余裕がある。カレンダーアプリが読みに来る回数は、購読している人数 × 1 日に数回〜24 回ほどで、団体のメンバーが数百人いても Workers の無料枠（1 日 10 万リクエスト）に収まる。

予約が増えても、1 回に返すのは終了が 90 日前より後の予約だけなので、iCal の大きさは団体の予約の頻度で決まり、運用の年数では増えない。

## トレードオフ

| 項目                                 | トレードオフ                                                                                       | 対策                                                                                                                                         |
| ------------------------------------ | -------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| URL が鍵になる                       | URL が漏れると、ログインせずに備考まで読まれる                                                     | 画面で、人に教えない・共有しているカレンダーに追加しないよう案内する。漏れたら本人が作り直し、前の URL はすぐに 0 件になる                   |
| トークンをハッシュにしない           | データベースが漏れると、作り直すまでその後の予約も読み続けられる                                   | 漏れた時点で予約はすでに読まれている。漏れが分かったら作り直してもらう。データベースを読める人を絞るのは Cloudflare のアカウントの管理で行う |
| Workers Logs に URL が残る           | ログを見られる人はトークンを知りうる                                                               | ログを見られるのは D1 も読める運用者だけである。アプリのログにはトークンを出さない                                                           |
| 見つからないときに 0 件を 200 で返す | URL を打ち間違えても、エラーにならず空のカレンダーになる                                           | URL はコピーかボタンで渡すので打ち間違えにくい。カレンダーの名前で無効だと分かる                                                             |
| 反映の遅れ                           | Google カレンダーは URL のカレンダーを数時間〜1 日おきにしか読み直さず、システムからは縮められない | 予約の状態の変化はメールで知らせる。遅れることを画面で案内する（COND-029 の (8)）                                                            |
| 読まれた記録を持たない               | 漏れた URL が実際に使われたかは分からない                                                          | 漏れたと思ったら作り直す運用にする（決定 8）                                                                                                 |
| ライブラリを使わず iCal を組み立てる | RFC 5545 の細かい規則（折り返し・逃がす文字）を自分で守る必要がある                                | 使う範囲を予定の数個の項目に限り、単体テストで固める。プレビュー環境で実際のカレンダーアプリに登録して確かめる                               |

## 適用範囲

本 ADR は、団体のメンバーへの自団体の予約のカレンダーの配信（REQ-050・UC-039・COND-029）に適用する。施設ごとの Google Calendar の同期（ADR-008）は変えない。
