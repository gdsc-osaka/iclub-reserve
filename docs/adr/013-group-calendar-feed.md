# ADR-013: 団体ごとの予約カレンダーは、Worker が返す iCalendar の購読 URL で配り、空き状況の画面は事務局専用にする

## ステータス

提案 (2026-10-23)

Issue #195 を受けて決める。施設ごとの Google カレンダーの同期（ADR-008）は変えない。

## コンテキスト

### 空き状況の画面は、団体にとっては他団体の予約ばかりが並ぶ画面になっている

空き状況カレンダー（SCR-001・`/availability`）は、施設 1 つの 1 週間分の予約を、他団体の予約も含めて並べる画面である。
事務局にとっては、承認・却下・直接作成をその場で行える、仕事の中心の画面になっている。

一方、団体の利用者がこの画面で知りたいのは、自分たちの予約と、申請したい時間が空いているかどうかだけである。
前者は予約一覧（SCR-003）とダッシュボード（SCR-022）で分かる。
後者は、予約申請フォーム（SCR-002）の日時の選択に、その日・その施設の予約が他団体の分も含めて並んでいるので、そこで確かめられる。
団体の利用者にとって、週全体に並ぶ他団体の予約は、自分たちの予約を見つけにくくするだけになっている。

### 団体の利用者は、自団体の予約を自分のカレンダーで見たい

施設ごとの Google カレンダー（ADR-008）は、施設がいつ埋まっているかを学内外に示すもので、団体名を載せない（COND-008 の (3)）。
自団体の予約がいつあるかは、このカレンダーからは分からない。
団体の利用者は、自分たちの予約（仮予約を含む）を、普段使っているカレンダーアプリに並べて見たい。

### 施設と同じ方式（Google カレンダーと Service Account）は、団体には向かない

施設のカレンダーは、事務局が共有の Google アカウントで作り、Service Account に「予定の変更」の権限を共有してから、そのカレンダーの ID を施設に設定する（ADR-008 の運用手順）。
同じ方式を団体に使おうとすると、次の問題がある。

1. **手順が団体の数だけ要る。** 施設は事務局が 1 回用意すれば済む。団体は利用者が登録するもので（UC-010）、登録のたびに事務局がカレンダーを作って共有することになる。
2. **自動にすると、扱う範囲が広がる。** Service Account にカレンダーを作らせて共有まで自動にすると、スコープを `calendar.events` から `calendar` に広げることになる。さらに、メンバーの加入・脱退のたびに共有の設定（ACL）を直す同期が要る。メンバーのメールアドレスが Google アカウントだとも限らない。
3. **Workers の上限の予算に乗らない。** ADR-008 は、毎分の同期を 5 件、日次の突き合わせを施設 40 前後までとして、Free プランのサブリクエスト上限（50 件）に収めている。団体の数だけ Google への呼び出しが増え、仮予約も載せるので同期のきっかけも増える。

## 決定

### 1. 空き状況カレンダー（SCR-001）は事務局専用にする

- ナビの「空き状況」は事務局にだけ出す（`staffNavItems`）。団体の利用者のボトムバーは「ダッシュボード・予約・カレンダー購読・所属団体」の 4 つになる。
- 画面そのものも事務局しか開けないようにする。ナビから消すだけでは、URL を知っていれば開けてしまう。どこからも辿れない画面が残ると、古いリンクから迷い込んだ人に「事務局向けの画面だ」と分からない。
  事務局かどうかの判定は読み取りの門番（`ensureStaff`）が持ち、ルートは結果を受け取るだけにする（ADR-004）。事務局でなければ 403 を返し、画面には「事務局だけが使える画面」と書いて、予約の申請と予約一覧への導線を出す。
- 団体の利用者は、空きを予約申請フォーム（SCR-002）の日時の選択で確かめる。週全体を見渡して空いている日を探す使い方はできなくなる。団体は使いたい日を先に決めてから申請することが多いので、これは受け入れる。
- 団体の利用者から空き状況へ向けていた導線（ダッシュボード・予約一覧が空のとき・申請の後）は、予約申請フォームか予約一覧へ向け直す。

事務局専用にすると、見る人によって項目を落とす処理（COND-008）と、申請できるかどうかの判定（COND-006）が要らなくなる。
読み取りは ADR-012 の 3 つの条件（門番 1 つ・見る人で形が変わらない・書き込まない）をすべて満たすので、ユースケースとポートを持たない関数 `findFacilityAvailabilityCalendar(db, args)` に移す（ADR-012 決定 7）。
事務局の画面なので、予約の帯は事務局のダッシュボードの「今日の予約状況」と同じく、すべて濃い色で描き、「自団体」の印は付けない。

### 2. 団体の予約カレンダーは、Worker が iCalendar（.ics）を返す購読 URL で配る

Google カレンダーは作らない。利用者のカレンダーアプリが取りに来たときに、Worker が D1 から予約を読んで iCalendar（RFC 5545）を組み立てて返す。

- Google カレンダー（「URL で追加」）・Apple カレンダー・Outlook のどれでも購読できる。
- 同期の Outbox・Cron・Google API は要らない。取りに来るたびに今の予約から組み立てるので、予約とのずれが起きない。
- 団体を抜けた人や削除された予約は、次に取りに来たときにカレンダーから消える。

### 3. URL は、利用者ごとに発行する秘密のトークンで守る

カレンダーアプリはログインの Cookie を送らないので、URL そのものが鍵になる。

- **利用者ごとに 1 つ**のトークンを発行する。団体ごとに 1 つにすると、メンバーが抜けるたびにトークンを作り直すことになり、残ったメンバー全員の購読が切れる。
- URL は `/calendar-feeds/<トークン>/<団体 ID>.ics` とする。1 つのトークンで、その人が所属している団体ごとのカレンダーを購読できる。カレンダーアプリは購読ごとに色を分けられるので、団体ごとに分けておく。
- 取りに来るたびに、トークンが有効な利用者のものか、その利用者がいまその団体に所属しているかを確かめる。どちらで落ちても同じ 404 を返し、どちらで落ちたかを見分けられないようにする。
- トークンは `crypto.getRandomValues` で作る 32 バイトの乱数（base64url で 43 文字）とし、新しい表 `calendar_feed_token`（`user_id` を主キーにして利用者の削除に連動・`token` に一意制約・`created_at`）に持つ。
- 発行と作り直しは、利用者がボタンを押したとき（POST）だけに行う。loader では書き込まない。作り直すと古い URL は即座に使えなくなる。
- トークンは平文のまま持つ。載せる項目を決定 4 で絞るので、漏れたときに知られるのは、ログイン済みの利用者なら誰でも画面で見られる範囲に限られる。平文なら URL をいつでも表示し直せる。
- トークンはログに残さない。エラーの `message` にも入れない。なお、Workers の観測ログには、リクエストの URL（トークンを含む）が残る。見られるのは Cloudflare のアカウントの管理者だけなので、これは受け入れる。
- `/calendar-feeds/` はログインの確認を通さない。`app/lib/auth/auth-redirect.ts` の `PUBLIC_PATH_PREFIXES` に足す。

### 4. 載せるのは、ログイン済みの利用者に開示する範囲（COND-008 の (2)）までにする

| 項目                   | 内容                                                                                              |
| ---------------------- | ------------------------------------------------------------------------------------------------- |
| カレンダー名           | 団体名（`X-WR-CALNAME`）                                                                          |
| 予定のタイトル         | 仮予約は `[仮予約] 施設名`、承認済みは `施設名`                                                   |
| 予定の状態（`STATUS`） | 仮予約は `TENTATIVE`、承認済みは `CONFIRMED`                                                      |
| 日時                   | 予約の開始・終了（UTC で書き、`VTIMEZONE` を持たない）                                            |
| 説明・URL              | 団体名・状態と、予約詳細（SCR-005）の URL                                                         |
| 予定の ID（`UID`）     | `<予約 ID>@iclub-reserve`。日時や施設が変わっても、同じ予定として更新される                       |
| 載せる予約             | 仮予約と承認済み（`calendarVisibleStatuses`）。取り消し・却下・キャンセルで終わったものは載せない |
| 載せる期間             | 終了日時が 90 日前以降の予約。過去の予定がすぐに消えると困るので残し、上限で大きさを抑える        |

- **仮予約にはタイトルに `[仮予約]` を付ける。** `STATUS:TENTATIVE` も付けるが、カレンダーアプリによっては見た目が変わらない。
- **使用人数・備考・理由・申請者は載せない。** URL は長く使い続ける合言葉で、貼り間違いや共有で漏れやすい。漏れても失うものが無い範囲に収めておけば、トークンの扱いを単純にできる（決定 3）。詳しい内容は、説明に入れたリンクからログインして見てもらう。
  後から備考を載せたくなったら、トークンをハッシュにして持ち（URL を表示し直せず、作り直すだけにする）、COND-008 を改める。

### 5. 置き場所

- 購読の可否を所属で判定するので、ADR-012 の素通しの読み取りには当たらない。ユースケース（`get-group-calendar-feed`）が、トークンから利用者を引き、所属を確かめてから、団体の予約を Query ポートで読む。
- iCalendar の文字列は、純粋な関数で組み立てる（行の折り返し 75 オクテット・`\`・`;`・`,`・改行のエスケープ・CRLF）。依存のライブラリは足さない。
- 配信は、React Router の resource route（loader が `text/calendar; charset=utf-8` の `Response` を返す）で行う。

### 6. PR の分け方

1. **この ADR と要件の更新、空き状況の事務局専用化**（決定 1）
2. **配信**: トークンの表とマイグレーション、iCalendar を組み立てる関数、ユースケース、配信のルート（決定 2〜5）
3. **購読の画面**: カレンダー購読（SCR-010）に「所属団体の予約カレンダー」の区画を足し、団体ごとに「Google カレンダーに追加」・URL のコピー・URL の作り直しを置く

## 検討した案

### 案 A: 団体ごとに Google カレンダーを作る（却下）

コンテキストに書いた 3 つの問題（手順が団体の数だけ要る・自動にすると扱う範囲が広がる・Workers の上限の予算に乗らない）のため。
Google カレンダーの利用者には変更がすぐに届くという利点はあるが、予約の今の状態は予約一覧で確かめられる。

### 案 B: トークンを団体ごとに 1 つにする（却下）

メンバーが抜けたときに、抜けた人の購読だけを止める方法が無い。作り直すと、残った全員が登録し直すことになる。

### 案 C: トークンを持たず、利用者 ID と秘密の鍵から HMAC で作る（見送り）

表が要らず、D1 が漏れてもトークンは漏れない。しかし、環境ごと（ローカル・プレビュー・本番）に秘密の鍵を用意して管理することになる。
載せる項目を決定 4 で絞るので、D1 が漏れたときにトークンだけが漏れないことの価値は小さい。

### 案 D: 空き状況をナビから消すだけにする（却下）

決定 1 に書いたとおり、どこからも辿れない画面が残る。
見る人で項目を落とす処理と申請の可否の判定も、団体の利用者がまだ開ける以上は消せない。

## 結果

- 団体の利用者は、週の空き状況を一覧できなくなる。空きは予約申請フォームの日時の選択で、1 日ずつ確かめる。
- 事務局が団体にも所属している場合、空き状況で自団体の予約に印が付かなくなる。自団体の予約は予約一覧で確かめる。
- Google カレンダーは、URL で購読したカレンダーを読み直す間隔が長い（最大 12 時間ほどとされ、利用者は早められない）。Apple カレンダーや Outlook は、これより早く読み直すことが多い。購読の画面に「最新の状態は予約一覧で確かめる」ことを書く。
- 配信は取りに来るたびに D1 を 3 回ほど読む（トークン・所属・予約）。カレンダーアプリが取りに来るのは数時間に 1 回ほどなので、上限には響かない。

## 適用範囲

空き状況カレンダー（SCR-001・UC-001）と、団体の予約カレンダー（UC-039・COND-029）に適用する。
施設ごとの Google カレンダー（ADR-008）・カレンダー購読の画面のうち施設の部分（UC-018）は変えない。
