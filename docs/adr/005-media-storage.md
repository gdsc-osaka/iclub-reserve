# ADR-005: 画像の保存と配信

## ステータス

提案 (2026-09-23)

施設管理画面 (SCR-009) で施設の写真を扱うにあたって決めた。
施設の写真は、この決定を最初に使う例である。今後の団体のロゴやユーザーのアイコンも、この決定に乗せる前提で書いている。
ADR-001 (読み取り専用モデルの分離) と ADR-004 (エラーの扱い) の層の切り方は変えない。

## コンテキスト

INFO-002 (施設・設備) には `photo_url` の列があるが、写真を置く場所も、登録する画面も無かった。
SCR-009 で事務局が写真を登録できるようにするには、次を決める必要がある。

- 写真のバイナリをどこに置くか。D1 に BLOB で入れるとデータベースの容量を食い、バックアップも重くなる
- 施設の写真のあとに、団体のロゴやユーザーのアイコンも置く見込みがある。種類ごとに置き場所を分けるか
- 画像をどう配信するか。アプリはすべての画面でログインを求めており、画像だけ誰でも見られるようにはしたくない
- 事務局が送ってくるファイルを、どこまで信用するか

アプリは Cloudflare Workers で動いており、D1・Queues と同じく Workers のバインディングで使えるものが扱いやすい。

## 決定

### 1. 画像は R2 に置き、バケットは環境ごとに 1 つにする

アプリが保存する画像はすべて Cloudflare R2 に置く。
バケットは環境ごとに 1 つで、画像の種類ごとには分けない。

| 環境                       | バケット                      | バインディング |
| -------------------------- | ----------------------------- | -------------- |
| `production`               | `iclub-reserve-media`         | `MEDIA`        |
| `preview` とローカルの開発 | `iclub-reserve-media-preview` | `MEDIA`        |

種類はキーの接頭辞で分ける。接頭辞の一覧は `app/infra/media/media-bucket.ts` の `MediaPrefix` に持ち、
施設の写真は `facilities/<写真名>` に置く。種類を足すときはこの表に行を足す。

種類ごとにバケットを分けると、種類を足すたびにバケットを作り、`wrangler.jsonc` の 3 か所
(トップレベル・`env.production`・`env.preview`) にバインディングを足すことになる。
見せる条件が同じ画像を分けても得るものが無い。

### 2. バケットを分けるのは、バケット単位の設定が違うものが出てきたとき

公開の有無・CORS・API トークンの範囲・保存する地域は、バケット単位でしか決められない。
これらが違う画像が出てきたときだけ、別のバケットを作る。
たとえば、誰でも見られるように公開したい画像や、バックアップを置く場所がこれに当たる。

### 3. 接頭辞は権限の境界ではない

Worker のバインディングはバケット全体を読み書きできる。接頭辞で読み書きの範囲を絞ることはできない。
誰に見せるかは、画像の種類ごとの配信ルートが決める (決定 4)。

### 4. 配信は Worker が R2 から読んで返し、ログインを必須にする

画像は種類ごとのリソースルートから返す。施設の写真は `/facility-photos/:photoName`
(`app/routes/facility-photos/$photoName/route.ts`) である。

- ログインしていない人には返さない
- 写真名が `^[a-z0-9]+\.(jpg|png|webp)$` に合わなければ、R2 を引かずに 404 を返す。`../` などで別の接頭辞の下を読まれないようにする
- `Cache-Control: private, max-age=31536000, immutable` を付ける。写真を差し替えると写真名が変わる (決定 7) ので、同じ URL の中身は変わらない。ブラウザが取りに来るのを最初の 1 回にする。`private` なので、途中の共有キャッシュには残らない
- `X-Content-Type-Options: nosniff` と `ETag` を付ける

`/media/*` のような汎用の配信ルートは作らない。団体のロゴのように、種類によって見せる相手が変わる (COND-011) ためである。

### 5. 署名付き URL は採らない

- Worker のバインディングでは発行できない。S3 互換 API のアクセスキーを、secret として環境ごとに持つ必要がある
- `<アカウント>.r2.cloudflarestorage.com` でしか使えない。独自ドメインでは使えず、CDN のキャッシュも効かない
- 発行のたびに URL が変わるので、ブラウザのキャッシュが効きにくい
- 期限内は、URL を知っている人なら誰でも見られる。見せる相手の判定がアプリの外に出る

### 6. 公開バケット (独自ドメイン・r2.dev) は採らない

見せる相手を制御できない。同じバケットに置く予定の団体のロゴには、秘匿したいものがある。
独自ドメインもまだ無い。バケットは r2.dev での公開も無効にしてある。

### 7. 写真名はアプリが付け、`photo_url` にはアプリ内の相対パスを入れる

写真名は `createId()` と拡張子 (`jpg` / `png` / `webp`) で作る。利用者が付けたファイル名は使わない。
`photo_url` の列には `/facility-photos/<写真名>` を入れ、R2 のキーは入れない。
こうしておけば、接頭辞や配信の仕方を変えても、DB の値を書き換えずに済む。

### 8. 受け付ける形式は JPEG・PNG・WebP、大きさは 5 MiB まで

形式はファイルの先頭のバイト (マジックナンバー) で判定する。

| 形式 | 先頭のバイト                                              |
| ---- | --------------------------------------------------------- |
| JPEG | `FF D8 FF`                                                |
| PNG  | `89 50 4E 47 0D 0A 1A 0A`                                 |
| WebP | `RIFF` で始まり、8 バイト目から `WEBP` (0 始まりで数える) |

ブラウザが送ってくる MIME タイプ (`File.type`) は、ファイル名の拡張子から決まるだけで中身を表さないので、判定には使わない。
R2 に保存する Content-Type と写真名の拡張子も、先頭のバイトから決める。
拡張子が中身と違うだけのファイル (中身が PNG の `photo.jpg` など) は、中身の形式として受け付ける。

送ってくるのはログインした事務局に限られ、配信時に `nosniff` を付けるので、判定しなくても画像以外として解釈されることは無い。
それでも判定するのは、画像でないファイルが写真として保存され、壊れた画像として配信されるのを防ぐためである (PR #137 のレビュー)。
判定するのは先頭の数バイトだけで、画像として正しく読めるかまでは確かめない。

次の形式は受け付けない。

- **GIF**: 施設の写真に動きは要らない。静止画なら JPEG・PNG で足りる
- **SVG**: 画像の中にスクリプトを書ける。配信の仕方を誤ると、アプリのオリジンでスクリプトが動く
- **HEIC / HEIF**: iPhone のカメラの既定の形式だが、Chrome と Firefox で表示できない。iPhone の Safari は、写真ライブラリから選んだ写真を JPEG に変換して送るので、多くの場合はそのまま受け付けられる
- **AVIF**: 主なブラウザで表示できるが、写真として送られてくることがまだ少ない。必要になったら判定の表に足す

`request.formData()` は本文をすべてメモリに読み込むので、読む前に `Content-Length` を見て、
6 MiB を超える送信はフォームの誤りとして返す。写真の 5 MiB に、ほかの入力欄と multipart の区切りの分を足した値である。

### 9. R2 に置いてから DB に書き、古い写真は DB の更新後に消す

1. 新しい写真を R2 に置く
2. DB に書く。失敗したら、1 で置いた写真を消してから失敗を返す
3. 写真を差し替えた・外したときは、DB の更新が成功した後に古い写真を消す

編集では、2 の更新文の条件に「読んだときの `photo_url`」を入れる (楽観的ロック)。
読んでから書くまでの間に別の人が写真を差し替えると、差し替え前の写真はもう 3 で消されている。
条件を入れずに書くと、消えた写真を指す行が残る。条件に合わなければ 1 件も書かずに競合 (`FACILITY_CONFLICT`) を返し、2 と同じく 1 で置いた写真を片付ける。

2 の片付けと 3 の削除は、失敗してもログに残すだけで、利用者には伝えない
(`app/usecases/facility/_shared/facility-photo.ts` の `deleteFacilityPhotoQuietly`)。
3 で失敗を返すと、更新は済んでいるのに利用者がやり直してしまう。
消し損ねた写真がバケットに孤立して残ることは許容する。どこからも参照されないので、見えることは無い。

### 10. 縮小・形式変換はまだ入れない

Cloudflare Images などによる縮小・形式変換は入れない。
施設は初期データで 8 件であり、一覧に並ぶ写真もその数に留まる。一覧が重くなったら検討する。

### 11. バケットは手作業で作った

2 つのバケットは、2026-09-23 に wrangler で作った。場所の指定は APAC、ストレージクラスは Standard、r2.dev での公開は無効である。
Terraform の管理下には無い。
`wrangler.jsonc` に書いたバケットが無いとデプロイが失敗するので、環境を増やすときは、先にバケットを作っておく必要がある。

```bash
CLOUDFLARE_ACCOUNT_ID=<アカウント ID> pnpm exec wrangler r2 bucket create <バケット名> --location apac
```

ログインしているアカウントが複数あると、`wrangler.jsonc` に `account_id` があっても wrangler はアカウントを選べずに失敗する。
`CLOUDFLARE_ACCOUNT_ID` で指定する。

## 層の割り当て

| 置き場所                                          | 中身                                                                                |
| ------------------------------------------------- | ----------------------------------------------------------------------------------- |
| `app/domain/facility/facility-photo.ts`           | 形式と大きさの検証、写真名の生成と判定、保存先のポート `FacilityPhotoStorage`       |
| `app/infra/media/media-bucket.ts`                 | 接頭辞の一覧 `MediaPrefix`                                                          |
| `app/infra/facility/r2-facility-photo-storage.ts` | ポートの R2 実装。写真名に接頭辞を付けてキーにするのはここだけ                      |
| `app/usecases/facility/`                          | 登録・編集で、決定 9 の順に R2 と DB を書く                                         |
| `app/routes/facility-photos/$photoName/route.ts`  | 配信 (決定 4)。業務ルールを持たない読み出しなので、ユースケースを挟まずポートを呼ぶ |

ドメインとユースケースは R2 のキーを知らない。ポートとは写真名だけでやりとりする。

## トレードオフ

- 画像を見るたびに Worker が動く。ただし `immutable` なので、同じ人が同じ画像を取りに来るのは最初の 1 回である
- 孤立した写真を掃除する仕組みは無い。溜まってきたら、DB の `photo_url` と突き合わせて消す作業を考える
- バケットを Terraform で管理していない。作り直すときは決定 11 の手順を手で行う
