# ADR-005: 施設写真等の静的メディア保存に Cloudflare R2 を採用する

## ステータス

承認 (2026-09-23)

## コンテキスト

施設管理機能（SCR-009 / BIZ-004）の実装にあたり、施設・設備（INFO-002）の写真（`photo_url`）など、利用者がアップロードする静的メディアファイルの永続化先が必要となった。

当システム `iclub-reserve` は Cloudflare Workers 上で動作するフルスタックアプリケーションであり、Edge ランタイムとの親和性、運用負荷、コスト、セキュリティの観点からメディア保存方針を決定する必要がある。

### 検討した選択肢

1. **Cloudflare R2（採用）**
   - Cloudflare の S3 互換オブジェクトストレージ。
   - 同一 Cloudflare アカウント内の Workers からバインディング（`R2Bucket`）経由で直接読み書きでき、ネットワーク越しの認証（API キーや IAM）が不要。
   - エグレス（データ転送）料金がゼロであり、小規模〜中規模の学内施設予約システムとして運用コストを極小化できる。

2. **Cloudflare Images（不採用）**
   - 画像変換・最適化配信に特化したマネージドサービス。
   - 動的なリサイズや形式変換の機能が豊富だが、最低利用料金（月額固定）が発生する。現時点の要件（施設写真の登録・表示）に対しては過剰であり、R2 単体で十分要件を満たせる。

3. **外部オブジェクトストレージ（AWS S3 等）（不採用）**
   - クラウド各社の標準的オブジェクトストレージ。
   - Cloudflare Workers からアクセスするためにアクセスキー・シークレットの管理が必要となり、インフラ構成および機密情報管理が複雑化する。またエグレス料金が発生する。

4. **Cloudflare D1（SQLite）への BLOB / Base64 保存（不採用）**
   - データベース内に画像バイナリを直接保存する方式。
   - 実装は容易だが、D1 のデータベースサイズ上限（10 GB）を圧迫し、バックアップ・レプリケーション・クエリパフォーマンスに深刻な悪影響を及ぼす。

## 決定

**静的メディア保存ストレージとして Cloudflare R2 を採用する。**

### 1. Workers バインディングによる接続

`wrangler.jsonc` の環境設定（ローカル、`env.preview`、`env.production`）に `r2_buckets` を定義し、バインディング名 `MEDIA` として Workers に注入する。

| 環境         | バケット名                       | バインディング名 |
| ------------ | -------------------------------- | ---------------- |
| `local`      | `iclub-reserve-media-preview`    | `MEDIA`          |
| `preview`    | `iclub-reserve-media-preview`    | `MEDIA`          |
| `production` | `iclub-reserve-media-production` | `MEDIA`          |

バケットのプレフィックス定義は `app/infra/media/media-bucket.ts` に集約し、施設写真は `facilities/<photo_name>` として配置する。

### 2. ポート・アダプタによる疎結合設計

ドメイン・ユースケース層は特定のストレージ実装に依存せず、ポートインターフェース（`FacilityPhotoStorage`）を介して操作する。

- **ポート**: `app/domain/facility/facility-photo.ts`（`putPhoto`, `deletePhoto`, `photoExists`）
- **アダプタ**: `app/infra/facility/r2-facility-photo-storage.ts`（Cloudflare R2 バインディング `R2Bucket` の実装）

これにより、単体テストではインメモリのスタブストレージを使用でき、Workers ランタイムへの依存をテストから排除できる。

### 3. 写真の命名規則とキャッシュ戦略

写真ファイル名は CUID2（英小文字数字24文字）＋拡張子（`.jpg` / `.png` / `.webp`）とし、アップロードごとに必ずユニークな名前を割り当てる。

URL が一意かつ不変（Immutable）であるため、配信時には `Cache-Control: private, max-age=31536000, immutable` を付与し、ブラウザおよび中間キャッシュを最大効率で活用する。写真変更時は新しい CUID2 で上書きではなく新規作成し、古い写真をストレージから削除する。

### 4. 認証付きリソースルートによる配信

R2 バケットはパブリック公開（Custom Domain や r2.dev）せず、React Router のリソースルート `/facility-photos/:photoName` 経由で Workers からストリーミング配信する。

- **認可**: ログイン済みユーザー（学内アカウント確認済み）のみ写真へのアクセスを許可する。
- **検証**: 写真名が CUID2 の英小文字数字＋許可拡張子のパターン（`^[a-z0-9]+\.(jpg|png|webp)$`）を満たすか検証し、パストラバーサルを完全に防ぐ。

### 5. 入力制限と形式検証

- **サイズ制限**: 5 MiB 上限。HTTP リクエストヘッダーの `Content-Length` で巨大リクエストを事前遮断し、Workers のメモリ枯渇を防ぐ。
- **形式検証**: 拡張子だけでなく、ファイル先頭の Magic Number（バイナリシグネチャ）を検証して JPEG / PNG / WebP 以外の偽装ファイルを拒否する。

## 結果と影響

### 利点

- **コスト最適化**: R2 のゼロエグレス料金により、画像表示に伴うデータ転送料金が発生しない。
- **高セキュリティ**: バケットを直接インターネットに公開せず、Workers の認可と入力検証を通した配信ルートのみを提供することで安全性を担保する。
- **保守性**: ポート・アダプタ構造により、将来のストレージ変更やキャッシュ戦略の変更が容易である。

### 制限と注意点

- **インフラ管理**: Terraform による Cloudflare リソース定義に `cloudflare_r2_bucket`（`iclub-reserve-media-production` および `iclub-reserve-media-preview`）を追加する必要がある。
- **ローカル開発**: ローカル環境（`pnpm run dev`）では Wrangler のローカルシミュレーション機能により `.wrangler/state/v3/r2` にファイルが保存される。
