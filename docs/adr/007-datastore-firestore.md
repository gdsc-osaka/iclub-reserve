# ADR-007: データストア選定 — Firestore

- **ステータス**: Accepted
- **決定日**: 2026-03-18
- **決定者**: GDG on Campus Osaka 開発チーム
- **関連 RDRA**: INFO-001〜006, COND-001, COND-003

---

## コンテキスト

情報モデル（INFO-001〜006）は予約・団体・メンバーシップ・メッセージなどリレーショナルな構造を持つ。これを管理するデータストアを選定する必要がある。

- Google Cloud / Firebase にインフラを統一する方針（ADR-001・002）
- 運用初期は学内の少数団体向けシステムであり、トラフィックは限定的
- 重複予約チェック（COND-001）・施設無効化前提条件チェック（COND-003）などのトランザクション・複合クエリが必要

## 選択肢

| 案 | 選択肢 | 採否 |
|----|--------|------|
| **A（採用）** | Firestore（NoSQL / ドキュメント型） | ✅ |
| B | Cloud SQL for PostgreSQL（リレーショナル DB） | ❌ |

### Cloud SQL を却下した理由

- 最小インスタンス（db-f1-micro）でも月額約 $7〜15 の固定費が無トラフィック時にも発生する
- 運用実績が出るまでのフェーズにおいてコスト効率が悪い
- Firebase Auth（ADR-001）・Google Calendar（ADR-002）との統合において、Firestore の方が SDK・プロジェクト管理の一貫性が高い

## 決定

**Firestore をデータストアとして採用する。**

### コレクション設計方針

RDRA の情報モデルを以下のトップレベルコレクションに対応させる。

| コレクション | 対応エンティティ |
|------------|---------------|
| `users` | INFO-006 ユーザー |
| `groups` | INFO-003 団体 |
| `memberships` | INFO-005 メンバーシップ（user_id・group_id を持つ中間コレクション） |
| `facilities` | INFO-002 施設/設備 |
| `reservations` | INFO-001 予約 |
| `messages` | INFO-004 メッセージ（`reservations/{id}/messages` サブコレクション） |

### 主要な設計上の注意点

**COND-001（重複予約チェック）**
同一施設・同一時間帯の承認済み予約の有無を確認してから書き込む処理を、Firestore トランザクション内で実行する。`facility_id` と `status`（`approved`）および `start_at` / `end_at` に複合インデックスを設定する。

**COND-003（施設無効化の前提条件チェック）**
対象施設の将来の予約（`provisional` / `approved`）が存在しないことを確認するクエリ。`facility_id` と `status` と `end_at` の複合インデックスで対応する。

**INFO-005（メンバーシップ・多対多）**
JOIN がないため、`user_id` と `group_id` の両方向からクエリできるよう `memberships` コレクションに両フィールドを持たせ、複合インデックスを設定する。

## 影響・トレードオフ

| 項目 | 内容 |
|------|------|
| コスト | 無料枠（読み取り 50,000回/日・書き込み 20,000回/日）内で運用初期は賄える見込み。超過時は従量課金 |
| Firebase 統合 | Firebase Auth（ADR-001）と同一 SDK・同一プロジェクトで管理できる |
| トランザクション | Firestore はトランザクションをサポートするが、クロスコレクションのトランザクションは上限（最大 500 ドキュメント）に注意する |
| 複雑クエリ | JOIN が使えないため、多対多のメンバーシップ解決や複数条件の集計はアプリ側で処理する。将来的に複雑な集計・レポートが必要になった場合は BigQuery へのエクスポートを検討する |
| スキーマ管理 | スキーマレスのため、アプリ側（型定義・バリデーション）でデータ整合性を担保する必要がある |
