# ADR-009: アカウントの有無が分かってしまう Better Auth の不備は、直さずに上流の修正を待つ

## ステータス

承認 (2026-10-14)

COND-018（メールアドレス変更の秘匿と後処理）の実装を調べ直したときに見つけた漏れの扱いを決める。
要件（REQ-035・COND-018）は変えない。実装状況表の COND-018 は 🟡 のままにして、理由をこの ADR に合わせて書き直す。

## コンテキスト

COND-018 は、メールアドレスの変更で新しいアドレスが別のアカウントで使われていても、
使われていない場合と同じ応答を同じ時間で返すことを求めている。
学内の誰がアカウントを持っているかを調べる手段にさせないためである。

これまでの実装状況表は、残る差を「使用済みのアドレスのときだけ D1 への書き込みが 1 回多い（応答時間のわずかな差）」としていた。
2026-10-14 に Better Auth 1.7.7 の email-otp プラグインのコードを読み、メモリ上の DB（`memoryAdapter`）で動かして確かめた。
すると、応答の中身からアカウントの有無を確実に判別できる経路が見つかった。次の 1〜3 である。

### 1. メールアドレスの変更：3 段階目のエラーで分かる

- 2 段階目（`/email-otp/request-email-change`、`requestEmailChangeEmailOTP`）は、新しいアドレス宛ての認証コードを DB（`verification`）に保存してから、そのアドレスが使用済みかどうかを引く。
  使用済みなら保存したコードを消し、`{ success: true }` を返す。未使用ならコードを残してメールを送る。
- 3 段階目（`/email-otp/change-email`）の照合（`atomicVerifyOTP`）は、コードが無ければ何度送っても `INVALID_OTP` を返す。
  コードがあれば、誤りが 3 回続いた後の 4 回目に `TOO_MANY_ATTEMPTS`（403）を返し、期限を過ぎていれば `OTP_EXPIRED` を返す。

| 3 段階目に違うコードを送る    | 新しいアドレスが使用済み | 新しいアドレスが未使用                                   |
| ----------------------------- | ------------------------ | -------------------------------------------------------- |
| 4 回続けて送る                | 4 回とも `INVALID_OTP`   | 3 回目までは `INVALID_OTP`、4 回目は `TOO_MANY_ATTEMPTS` |
| 期限（5 分）を過ぎてから 1 回 | `INVALID_OTP`            | `OTP_EXPIRED`                                            |

画面（SCR-017）からでも分かる。3 段階目で違うコードを入れ続けると、未使用なら「認証に何度も失敗したため…」に変わり、使用済みなら「認証コードが正しくありません」のままになる。
調べる側に要るのは自分のアカウントと、調べるアドレス 1 件につき自分宛ての認証コード 1 通である。
期限切れを使えば 3 段階目は 1 回送るだけで済むので、Better Auth の回数制限では防げない。

### 2. メール確認用の認証コード：ログインしていなくても同じ仕組みで分かる

`/email-otp/send-verification-otp` を `type: "email-verification"` で呼ぶと、Better Auth はコードを保存してから利用者を引く。
アカウントが無ければコードを消し、`{ success: true }` を返す（送らない）。
続けて `/email-otp/verify-email` に違うコードを 4 回送ると、アカウントがあれば 4 回目が `TOO_MANY_ATTEMPTS` になり、無ければ 4 回とも `INVALID_OTP` になる。

ログインは要らない。このアプリの `hooks.before` は、阪大のアドレスなら種別を問わず通す。
ただし、アカウントがある人には身に覚えのない認証コードのメールが届くので、調べられた側は気づける。
2026-10-08 の変更（change-log.md、REQ-033）で、ログイン画面（SCR-012）に「入力されたアドレスが未登録かどうか」を出さないと決めた理由に反する。

### 3. 阪大以外のアドレスでのログイン：このアプリの規則で分かる

COND-004 により、阪大以外のアドレスへの認証コードの送信は、アカウントが無ければ 403（`EMAIL_DOMAIN_NOT_ALLOWED`）、あれば 200 になる（`checkSendVerificationOtpRule`）。
阪大以外のアドレスについては、アカウントの有無がそのまま分かる。これは Better Auth ではなく、このアプリの規則から来る。

### 4. Better Auth の公式の扱い

- セキュリティのドキュメントの「Email Enumeration Protection」は、新規登録と本体の `/change-email` で、登録の有無を漏らさないとしている。
  本体の `/change-email` は、使用済みのアドレスにも同じ応答を返し、トークンを作る処理も同じように走らせて応答時間をそろえる（better-auth/better-auth#8097）。
  本体の方式は署名付きのトークンをリンクで送るだけで DB に保存しないので、後から外から見える違いが残らない。
- email-otp プラグインのドキュメントは、メールアドレスの変更での秘匿に触れていない。
  関係する記述は「タイミング攻撃を避けるため、メールの送信を待たない（サーバーレスでは `waitUntil` などを使う）」だけで、このアプリは `advanced.backgroundTasks` で既にそうしている。
- プラグインも 2 段階目では応答をそろえていて、隠すつもりはある。
  3 段階目のコードには「正しいコードを持っている人には、使用済みだと漏れても安全」という趣旨のコメントがある。正しいコードを持たない段階でエラーの種類が変わることは考えられておらず、見落としと読める。
- 2026-10-14 時点で、この件の issue・PR は見つからない。最新のリリース 1.7.7 も、`main`・`next` ブランチも同じコードである。

## 決定

### 1. 1〜3 は今は直さず、受け入れる

分かるのは「そのアドレスで i-Club 予約システムのアカウントを持っているか」だけである。
氏名・所属団体・予約などは分からない。アカウントがあると分かっても、ログインはできない（そのアドレスの受信箱かパスキーが要る）。
調べる側にも、1 件ごとに自分宛ての認証コード 1 通（1）か、相手へのメール 1 通（2）の手間がかかる。
3 は手間がかからないが、分かるのは阪大以外のアドレスに限られる。
万が一使われても致命的な問題にはならないと判断した。

### 2. 回避策は入れず、Better Auth の修正を待つ

1 と 2 の原因は Better Auth にある。上流で直すなら、「使用済み（2 では未登録）のときもコードを消さず、送らないだけにする」で済むはずである。
コードは誰にも届かないので当てられず、照合のエラーの種類がそろい、D1 への書き込みの差も無くなる。

アプリ側で埋める案も検討したが、得られるものに比べて保守の負担が大きいので採らない。

| 案                                                                        | 採らない理由                                                                                                                                             |
| ------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 使用済みのとき、after フックで届かないコードを置き直す                    | Better Auth 内部の形式（識別子 `change-email-otp-<今のアドレス>-<新しいアドレス>`、値 `コード:回数`）に頼る。D1 への書き込みが増え、応答時間の差は広がる |
| 3 段階目の `OTP_EXPIRED`・`TOO_MANY_ATTEMPTS` を `INVALID_OTP` にまとめる | 期限切れ・回数超過の案内を出せなくなる。2 は塞がらない                                                                                                   |
| 応答までの時間に下限を設ける                                              | 応答時間の差しか消せない                                                                                                                                 |
| `pnpm patch` で、コードを消す処理を外す                                   | Better Auth を上げるたびにパッチを合わせ直す必要がある。このプロジェクトにはまだパッチを当てる運用が無い                                                 |

3 はこのアプリの規則から来る。塞ぐには、阪大以外の未登録のアドレスにも 200 を返して何も送らないことになり、
阪大以外のアドレスを入れてしまった人に理由を伝えられなくなる。決定 1 と同じ判断で、今の案内を優先する。

### 3. Better Auth を上げるときに確かめる

email-otp プラグインの `requestEmailChangeEmailOTP` と `sendVerificationOTP` が、使用済み（未登録）のときに保存したコードを消しているかを見る。
消さなくなっていれば、次のことをする。

- 1 と 2 の判別ができなくなったことを、コンテキストの表の手順で確かめる。
- 使用済みのときだけ D1 への書き込みが 1 回多い差も消えるはずなので、COND-018 を ✅ にできるか見直す。
- この ADR のステータスを更新する。

## トレードオフ

- 上流が直すまで、COND-018 は 🟡 のまま残り、要件（REQ-035・COND-018）と実装が食い違う。
- 上流へはまだ報告していない。報告したら、その issue を「関連」に書き足す。
- アカウントを持っていること自体が守るべき情報になったら（たとえば、利用者の範囲や扱う情報が変わったとき）、この判断を見直す。
