# ADR-011: ホーム画面に追加して使えるようにする（PWA）

## ステータス

提案 (2026-10-15)

プッシュ通知は扱わない。要件から別に決める（決定 1）。

## コンテキスト

このシステムは、団体のメンバーがスマホから申請し、事務局が承認する使い方が多い。毎回ブラウザを開いて URL やブックマークをたどるのは手間なので、ホーム画面のアイコンから一度で開けるようにしたい。

PWA にすると得られるものは主に 3 つある。

| 得られるもの                             | このシステムでの価値                                                                                            |
| ---------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| ホーム画面のアイコンから、単独の窓で開く | 大きい。手間がほとんどかからない                                                                                |
| オフラインでも開ける                     | 小さい。予約は常にサーバーの状態が正で、手元の写しを見せても役に立たない（決定 3）                              |
| プッシュ通知                             | 大きいが、表・宛先・設定画面が増え、要件（RDRA）から決める必要がある。iPhone はホーム画面に追加したときだけ届く |

ブラウザの事情は次のとおり（2026-10 時点）。

- Chrome は、メニューからのインストールに Service Worker を求めなくなった。ただし、自動のインストール案内（`beforeinstallprompt`）には、今も fetch を受け持つ Service Worker を求める。
- iOS 26 では、manifest が無くても「ホーム画面に追加」で Web アプリとして開く。manifest は名前・アイコン・色を決めるために使われる。
- iPhone のホーム画面のアプリは、Safari と Cookie・ストレージを共有しない。

## 決定

### 1. 段階に分け、まずは「ホーム画面から開ける」ところまでにする

この ADR で入れるのは、manifest・アイコン・オフラインの画面を出すだけの Service Worker である。

プッシュ通知は別に進める。入れるときは、どのイベントで送るか・メールに足すのか置き換えるのか・端末ごとにオン・オフできるかを RDRA で決めてから、別の ADR を書く。iPhone ではホーム画面に追加しないと届かないので、「ホーム画面に追加」の案内を画面に出すかどうかも、プッシュ通知と一緒に決める。

### 2. manifest・アイコン・Service Worker は public/ の静的ファイルにする

| ファイル                              | 役割                                                         |
| ------------------------------------- | ------------------------------------------------------------ |
| `public/manifest.webmanifest`         | 名前（i-Club 予約システム／i-Club 予約）・アイコン・開き方   |
| `public/icons/icon-{192,512}.png`     | ホーム画面・インストールしたアプリの窓のアイコン（角丸）     |
| `public/icons/maskable-512.png`       | Android が丸や角丸に切り抜いて使うアイコン                   |
| `public/icons/monochrome-512.png`     | 1 色で塗り直して使うアイコン（背景なし。下の注を参照）       |
| `public/apple-touch-icon.png`         | iPhone・iPad のホーム画面のアイコン（iOS が角を丸める）      |
| `public/favicon.ico`                  | ブラウザのタブのアイコン（16・32・48px）                     |
| `public/sw.js`・`public/offline.html` | オフラインの画面を出す Service Worker と、その画面（決定 3） |

- Workers の静的ファイルは Worker より先に返されるので、`app/root.tsx` のログイン必須のミドルウェアを通らない。React Router のルートで返すと、ログインしていない人は `/login` へ送られて読めなくなる。
- ブラウザは manifest を、ふつうは Cookie なしで取りに行く。ブランチのプレビュー（`*.iclub-preview.gdgoc-osaka.jp`）は Cloudflare Access の内側にあり、Cookie が無いとどのパスも Access のログインへ転送される。そのため manifest を読めず、Android の Chrome で「このアプリはインストールできません」になった（`develop` のプレビューは Access の外にある）。`<link rel="manifest">` に `crossorigin="use-credentials"` を付けて、Cookie 付きで取りに行かせる。同じ origin の静的ファイルなので、本番で Cookie が付いても害はない。
- アイコンは、ロゴの稲妻（`app/components/brand/iclub-bolt.ts`）を黒（ロゴの文字の色）の上に置いて作る。白の背景では黄色の稲妻が読みにくい。`pnpm run icons:generate`（`scripts/generate-app-icons.ts`）が、E2E で使っている Playwright の Chromium で SVG を描いて PNG と ICO を書き出す。画像の変換のためだけに依存を増やさないためである。作った画像はリポジトリに含め、稲妻や背景色を変えたときだけ作り直す。
- 1 色のアイコン（`purpose: "monochrome"`）は、使う側が色を捨てて形だけを使うので、背景を敷かずに稲妻だけを描く。Android のテーマアイコン（壁紙の色に合わせて塗り直すアイコン）に使われることを期待して置くが、2026-10 時点の Chrome は、Android でインストールしたアプリ（WebAPK）にこのアイコンを渡していない（Chromium の `components/webapk/webapk.proto` に「使っていないので無視する」とある）。そのため、テーマアイコンを有効にした Android でも、今は通常のアイコンのまま出るはずである。置いておけば、Chrome が対応したときに manifest を変えずに使われる。
- 上の帯（ステータスバー・タイトルバー）の色は、ページの `<meta name="theme-color">` にライト・ダーク別（`media="(prefers-color-scheme: ...)"`）で書き、画面の上端の帯と同じ背景色にそろえる。
- manifest には `theme_color` を書かない。manifest にはライト・ダーク別の色を書けず（Chromium にはダーク用の欄 `dark_theme_color` があるが、廃止予定の実験の名残で、manifest からは読まれない）、白を固定で書いていたときは、ダークモードの Android でインストールしたアプリのステータスバーが白いままになった。書かなければ、ページの `theme-color` か端末のテーマに従う。
- 起動時の画面（スプラッシュ）の背景（`background_color`）は、ダークの背景と同じ黒（`#0a0a0a`）にする。こちらも 1 色しか書けないので、白にするとダークモードで起動したときに白く光る。ライトモードでは一瞬だけ黒い画面が出るが、まぶしさの方を避ける。

### 3. Service Worker は、電波が無いときにオフラインの画面を出すことだけをする

画面（HTML）・画面のデータ（`.data`）・認証の API・画像は、一切キャッシュしない。

- 画面はログインしている人ごとにサーバーで組み立てており、権限によって見える項目も変わる（COND-008）。手元に写しを残すと、ログアウトした後や、同じ端末を使う別の人に、前の人の画面を見せてしまう。
- 予約の状態は事務局の操作で変わる。古い写しを見せると、承認済みかどうかを取り違える。
- デプロイの後に、古い JS と新しい画面が食い違う原因にもなる。

Service Worker が受け持つのは、画面そのものを開く GET（`mode: "navigate"`）だけで、サーバーに届かなかったときだけ `offline.html` を出す。サーバーが 500 などを返したときは、その応答をそのまま出す。画面を開くたびに Service Worker を通る分の待ち時間は、navigation preload で消す。

`offline.html` は Service Worker が入るときに一度だけ取り込む。このとき、中身だけを詰め直してから入れる。Workers の静的ファイルは `/offline.html` を `/offline` へ転送するので、受け取った応答をそのまま画面の代わりに返すと、ブラウザが受け付けずに読み込みが失敗する（`net::ERR_FAILED`）。

Service Worker は一度入ると利用者の端末に残り続け、壊れた版を出すとサーバー側を直しても治らない。処理は増やさず、増やすときはこの ADR を改める。万一のときは、自分を登録解除するだけの `sw.js` に差し替えて配る。

### 4. 開発サーバーでは Service Worker を登録しない

`app/root.tsx` は、本番向けのビルド（`import.meta.env.PROD`）でだけ登録する。localhost のポートは他のプロジェクトとも共有されるので、開発サーバーで登録すると、同じポートで動かした別のプロジェクトの画面までこの Service Worker を通ってしまう。試すときは `pnpm run preview` でビルドしたものを開く。

### 5. E2E は UC の外に 1 本だけ置く

`e2e/pwa/pwa.spec.ts`（タグ `@PWA`）で、次の 2 つを確かめる。UC に属さない仕組みなので、ADR-007 の「1 ファイル 1 UC」の例外とする。

- ログインしていなくても、manifest とアイコンが取れる（5 種類のブラウザ）
- ログインした画面を開いた後で通信を止めて開き直すと、前の画面の写しではなく、オフラインの画面が出る（Chromium だけ。通信を止めたときに Service Worker を通る動きを確かめられるのが Chromium だけのため）

## 採らなかった案

| 案                                                                    | 採らなかった理由                                                                                       |
| --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| Service Worker を置かない（manifest だけ）                            | Android の Chrome で自動のインストール案内が出ない。電波が無いときにブラウザの既定のエラー画面になる   |
| 画面やデータもキャッシュし、オフラインでも見られるようにする          | 決定 3 の理由で、秘匿と正確さを損なう。予約はオフラインで申請・承認できるものでもない                  |
| Workbox などのライブラリで Service Worker を作る                      | することが 1 つだけなので、依存を増やすほどの量にならない                                              |
| manifest を環境ごとに Worker で組み立てる（プレビューは名前を変える） | プレビューをインストールするのは開発者だけで、今は困っていない。必要になったら `workers/app.ts` で返す |

## 影響

- iPhone では、ホーム画面のアプリの中でもう一度ログインが要る（Safari と Cookie を共有しないため）。パスキーは iCloud キーチェーンにあるので、そのまま使える。
- iPhone では、通知メールのリンクはホーム画面のアプリではなく Safari で開く（iOS はリンクをアプリへ振り向けない）。今より悪くはならないが、PWA にしても変わらない。Android の Chrome は Cookie を共有し、リンクもアプリで開ける。
- iPhone では、Safari とホーム画面のアプリのログインが別のセッションになる。ログイン中の端末の一覧（REQ-044）では、どちらも同じ端末名（COND-020）で並ぶ。パスキーの登録の案内の記録（COND-010）も localStorage にあるので、アプリ側では最初からやり直しになる。
- iPhone のホーム画面から開くと、ブラウザの戻る・再読み込みのボタンが無く、引っ張って更新する操作もない。

## 残っていること

- 実機（iPhone・Android）で、ホーム画面から開いたときの見た目を確かめる。とくに、ボトムバーがホームバーと重ならないか（`viewport-fit=cover` が無いので `env(safe-area-inset-bottom)` が効いていない可能性がある）と、上のステータスバーの色がライト・ダークの両方で画面と合うか（Android では manifest の変更がすぐには反映されないので、インストールし直して確かめる）。
- 深い画面（予約の変更・団体の詳細・施設の編集など）から、画面の中のリンクで戻れるかを見直す。
- プッシュ通知と「ホーム画面に追加」の案内は、決定 1 のとおり別に進める。
