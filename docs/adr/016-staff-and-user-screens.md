# ADR-016: 事務局の画面と利用者の画面を URL で分け、立場は開いている画面で決める

## ステータス

提案 (2026-10-27)

Issue #238 を受けて決める。業務のルールは COND-030（`rdra/contexts/reservation-approval.md`）に書いてある。作業は 2 段階に分ける（決定 1）。1 段階目（外枠・ナビ・ダッシュボードを分け、切り替えを付ける）で決めたことを決定 1〜9 に、2 段階目（立場を画面で決める）で決めたことを決定 10〜18 に書く。

## コンテキスト

今は、事務局の人には、利用者向けのナビ・ダッシュボードと、事務局向けの機能が同じ画面に並んでいる（#238）。

- **画面が複雑に見える。** 事務局から見ると、ふだん使わない団体の機能が混ざる。スマホでは「その他」に 6 項目が入る。
- **どちらの立場で操作しているのか分からない。** 団体と事務局の両方に所属する人の立場を、システムが所属から推し量っている。自分の団体の予約にメッセージを送ると必ず団体側の送信になり、予約を変えると必ず事務局の直接変更になる。
- **コードが複雑になっている。** ダッシュボードの loader とコンポーネントが、事務局用と一般用の 2 つの画面を出し分けている。権限の判定にも、所属を読むものと読まないものが 2 本ずつある。

COND-030 は、事務局の画面と利用者の画面を分けて切り替えて使い、立場は開いている画面で決める、と定めた。この ADR は、それを URL・外枠・ダッシュボードでどう作るかを決める。

## 決定

### 1. 2 段階に分ける

1. **業務のルールは変えない。** 外枠・ナビ・ダッシュボードを利用者の画面（`/`）と事務局の画面（`/staff`）に分け、切り替えを付ける。予約の詳細などは、今までどおり両方の立場の操作を出す。
2. **立場を画面で決める。** 予約の詳細・空き状況・予約の作成と変更・団体管理に事務局の画面のルートを足し、操作する人（`Actor`）を画面から組み立てる。通知メールのリンクを直す。所属を読む・読まないの 2 本立てなど、両方の立場を前提にしたコードを片付ける。

1 段階目だけでも、事務局の人の画面は使いやすくなる。2 段階目は、ユースケースに渡す値が変わるので、分けたほうが見直しやすい。

### 2. どちらの画面かは URL のパスで決める

- `/staff` と `/staff/...` は事務局の画面とする。`/staff-invitations/...`（事務局招待の承諾）は、招待される人がまだ事務局ではないので、事務局の画面に含めない。
- 利用者の画面は、`/`（ダッシュボード）・`/reservations`（自団体の予約一覧）・`/groups`（所属団体の一覧）・`/groups/new`（団体の登録）とする。
- 両方に置く画面（空き状況・予約の作成・予約の詳細・予約の変更・団体の管理）は、1 段階目では利用者の画面の URL しか無い。これらと、どちらにも属さない画面（アカウント設定・招待の承諾）は、外枠を決めるうえで「どちらでもない」として扱う（決定 3）。2 段階目で事務局の画面の URL を足し、両方に置く画面もどちらかに決めた（決定 10）。
- Cookie やサーバーの状態には持たない。タブを 2 つ開いて別々の画面で操作しても食い違わず、メールのリンク・ブックマーク・戻るボタンがそのまま動く。サーバーはリクエストのパスだけでどちらの画面か分かる。

### 3. 「どちらでもない」画面では、最後に使った画面のナビを出す

事務局の画面から予約の詳細やアカウント設定を開いたときに、ナビが利用者の画面のものに変わると、どこにいるのか分からなくなる。そのため、「どちらでもない」画面では、そのタブで最後に開いていた画面のナビを出す。

- 最後に開いていた画面は、外枠のコンポーネントが覚えておく（React の状態）。決まった画面を開くたびに更新する。
- ページを読み込み直したときに備えて、ブラウザの Cookie（`iclub-reserve.last-area`。値は `staff` か `user`）にも書く。外枠の loader はこれを読んで、最初の描画を決める。Cookie が無ければ、事務局には事務局の画面のナビを出す（決定 4 と同じく、初めては事務局の画面）。
- Cookie に書くのは事務局の人だけで、ブラウザから書く。1 年保つ。中身は「どちらの画面か」だけで、誰のものかは分からない。
- この Cookie は、ナビの出し方とログイン後の行き先（決定 4）にしか使わない。権限の判定と、操作する人の立場には使わない（COND-030 の (4)）。書き換えられても、出るナビが変わるだけである。

### 4. ログイン後は `/start` を通し、前回使っていた画面のダッシュボードへ送る

- 画面を持たないルート `/start` を足し、その loader で行き先を決めて転送する。事務局には、Cookie（決定 3）が `user` なら `/` を、それ以外（`staff`・無い）なら `/staff` を開かせる。事務局でない人は、いつも `/` へ送る。
- ログイン後の既定の行き先（遷移先の指定が無いとき）を `/` から `/start` に変える。ログイン・お名前の登録・パスキーの案内は、どれも最後にこの行き先へ進むので、`/start` の判定だけで済む。
- 遷移先のパスが `/` のときも（`/?utm_source=mail` のようにクエリが付いていても）、既定と同じに扱って `/start` へ送る。ログインしていない人がアドレスを打って開くのは `/` だからである。
- ホーム画面に追加したアプリ（PWA）も、開くと `/start` を通す（`start_url`）。マニフェストに `id` を書いてあるので、`start_url` を変えても別のアプリとはみなされない（ADR-011）。
- ログインしている人が `/` を直接開いたときは、URL のとおり利用者の画面のダッシュボードを出し、転送しない。`/` を転送すると、事務局が利用者の画面のダッシュボードを開けなくなるうえ、決定 2 の「URL で決める」が崩れる。

### 5. 切り替えは「その人が行ける画面の一覧」から作る

- 行ける画面の一覧（事務局なら利用者の画面と事務局の画面、そうでなければ利用者の画面だけ）を返す関数を 1 つ置き、切り替えはそれを並べて描く。2 つ以上あるときだけ出す。「事務局か、そうでないか」の 2 択で書かないのは、システム運用の画面（#188）を 3 つ目として足せるようにするためである。
- PC・タブレットではサイドバーの上（ロゴの下）、スマホでは上部の帯の右端に置く。どの画面からも押せ、いまどちらの画面にいるかを常に示す。
- 押すと、もう一方の画面へ移る（リンク）。1 段階目では、両方に置く画面にまだ事務局の画面の URL が無いので、いつももう一方の画面のダッシュボードへ移した。2 段階目からは、両方に置く画面では同じものへ移す（決定 16）。
- もう一方の画面のナビに件数が付いていれば、切り替えのその画面に点の印を付ける。数字にしないのは、「その他」の印と同じく、種類の違う件数（承認待ちの予約と団体など）を足しても意味が無いためである。どの件数かは、移った先のナビで分かる。

### 6. ナビの項目は画面ごとに持つ

| 画面         | サイドバーの項目                                                                                                             | ボトムバーに直接並べる項目                   | 入口の文言 |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- | ---------- |
| 利用者の画面 | 「ダッシュボード」「空き状況」「予約」「所属団体」                                                                           | 「ダッシュボード」「空き状況」「予約」       | 予約を申請 |
| 事務局の画面 | 「ダッシュボード」「空き状況」「予約の承認」「団体の管理」「施設・設備の管理」「カレンダー購読」「操作履歴」「事務局の管理」 | 「ダッシュボード」「空き状況」「予約の承認」 | 予約を作成 |

- 事務局でない人のナビは、今と変わらない。
- 入口の文言は、開いている画面で決める（今は事務局かどうかで決めている。ADR-014 決定 9）。1 段階目では、入口の先のフォームはまだ事務局に両方の作り方を出した。2 段階目で、入口を画面ごとに分け（`/reservations/new` と `/staff/reservations/new`）、先の欄の作り方も画面で 1 つに決めた（決定 13）。
- 空き状況は両方の画面に置く（COND-030 の (3)）。1 段階目では、どちらのナビからも `/availability` を開いた。2 段階目から、事務局の画面のナビは `/staff/availability` を開く（決定 10）。

### 7. ナビの件数は画面ごとに数える

- 利用者の画面のダッシュボード: 団体側の未読と、自分宛ての招待の数（今の事務局でない人と同じ）。
- 事務局の画面のダッシュボード: 団体からの未読メッセージのある予約の数。
- 予約の承認・団体の管理: 今と同じ。

今は事務局のダッシュボードの件数に、この 3 つをすべて足している。ダッシュボードが分かれるので、件数もそれぞれのダッシュボードに並ぶ行の数にそろえる。

### 8. ダッシュボードを 2 つのルートに分ける

- `/`（`app/routes/home/`）は利用者の画面のダッシュボードとし、事務局が開いても事務局でない人と同じものを出す（SCR-022）。
- `/staff`（`app/routes/home/staff/`）は事務局の画面のダッシュボードとし、今の事務局用の区画を移す。「所属団体」の区画（自分の団体の未読・今後の予約・招待）は出さない。それらは利用者の画面で見る。
- loader とコンポーネントで事務局かどうかを分岐していたのをやめ、ルートごとに 1 つの画面にする。仮予約の承認・却下は `/staff` の action だけが受ける。
- `/staff` の loader は、区画を読む前に事務局かどうかを確かめ、事務局でなければ 403 にする。区画は読めなくても画面を開く作りなので、先に確かめないと、事務局でない人に区画が空のダッシュボードを見せてしまう。
- 利用者の画面のダッシュボードの「団体の最近の動き」は、事務局が開いても事務局でない人として読む（操作者を「事務局」と出す。COND-030 の (2)）。今まで事務局には出していなかった区画なので、1 段階目から画面の立場に従わせても、今の振る舞いは変わらない。

### 9. 1 段階目では、ほかの画面の立場は変えない

予約の詳細・空き状況・予約の変更・団体の管理・メッセージは、今までどおりセッションの `is_staff` で判定する。事務局が利用者の画面のナビから開いても、事務局の操作が出る。2 段階目で、これらに事務局の画面のルートを足すときに直す。

2 段階目で、この決定は決定 12〜14・18 に置き換えた。

### 10. 両方に置く画面に、事務局の画面の URL を足す

COND-030 の (3) で両方に置く画面に、事務局の画面の URL を足す。

| 画面                          | 利用者の画面             | 事務局の画面                   |
| ----------------------------- | ------------------------ | ------------------------------ |
| 空き状況カレンダー（SCR-001） | `/availability`          | `/staff/availability`          |
| 予約の作成の入口（SCR-002）   | `/reservations/new`      | `/staff/reservations/new`      |
| 予約の変更の入口（SCR-002）   | `/reservations/:id/edit` | `/staff/reservations/:id/edit` |
| 予約の詳細（SCR-005）         | `/reservations/:id`      | `/staff/reservations/:id`      |
| 団体管理（SCR-007）           | `/groups/:id`            | `/staff/groups/:id`            |

- 事務局の画面のルートは、ほかの事務局の画面と同じく、機能のフォルダの下の `staff/` に置く（例: `app/routes/reservations/staff/$reservationId/route.tsx`）。ルートのファイルは「どちらの画面か」を決めるだけにし、loader・action・画面の部品は利用者の画面と共有する（どちらの画面かを引数で受け取る）。
- 決定 2 の利用者の画面は、`/`・`/availability`・`/reservations` とその下・`/groups` とその下になる。「どちらでもない」画面は、アカウント設定と招待の承諾（`/invitations/...`・`/staff-invitations/...`）だけになる。

### 11. 事務局の画面のルートは、事務局でなければ 403 にする

- 事務局の画面のルートは、loader でも action でも、何かを読む前に事務局かどうかを確かめ、事務局でなければ 403 にする（決定 8 の `/staff` と同じ）。action でも確かめるのは、loader を通らずに送られてくることがあるためである。
- この確かめと、ユースケースに渡す立場（決定 12）は、1 つの関数で行う。両方に置く画面のルートは、セッションの `is_staff` をユースケースに直接渡さない。渡すと、利用者の画面で事務局の権限が使われる。

### 12. 操作する人（Actor）は、開いている画面から組み立てる

- 事務局の画面では `{ isStaff: true, membership: null }` とし、所属を読まない。利用者の画面では、事務局であっても `{ isStaff: false, membership }` とする（COND-030 の (1)）。
- ユースケースの引数の `isStaff` は、「事務局の画面からの操作か」を表すことになる。名前は変えず、意味をコメントに書く。事務局だけの画面のユースケースも同じ名前の引数を持っていて、そこでは今の意味（セッションの `is_staff`）のままでも食い違わないためである（事務局の画面にしか無く、決定 11 で事務局しか通らない）。
- 所属を読む・読まないの 2 本立て（`resolveGroupActor` と `resolveGroupActorWithMembership`、`resolveReservationActor` と `resolveReservationActorWithMembership`）を、1 本ずつにする。所属を読むかは「事務局の画面か」だけで決まり、操作の種類や記録の都合で読み分ける必要が無くなる。
- ドメインの判定（`isSentAsStaff`・`isActedAsStaff`・`resolveEditMode`・`canAct`）は変えない。Actor の組み立て方が変わることで、COND-030 の (2) のとおりになる。
  - メッセージ: 事務局の画面から送ると事務局としての送信、利用者の画面から送ると団体側の送信になる。
  - 操作履歴: 事務局の画面からの操作は `acted_as_staff` が true、利用者の画面からは false になる。
  - 予約の変更: 事務局の画面からは直接変更（UC-008）、利用者の画面からは団体の変更（UC-005・UC-017）になる。

### 13. 予約の作り方は、画面で 1 つに決める

- 空き状況カレンダーの欄（ADR-014 決定 10・11）で作る予約は、事務局の画面では直接作成（UC-008）、利用者の画面では仮予約の申請（UC-002）だけにする。「承認済みとして直接作成する」切り替えと、フォームの `mode` はなくす。どちらで作るかはサーバーが画面で決め、送られてきた値では決めない。
- 事務局の画面の欄は、解錠の手配（COND-027）をいつも選ばせ、申請元に有効な全団体を出す。利用者の画面の欄は、事務局でも所属する有効な団体だけを出す。

### 14. 受け付ける操作も、画面で絞る

- 予約の詳細の action は、事務局の画面では事務局の操作（承認・却下・事務局キャンセル）とメッセージだけを、利用者の画面では団体の操作（取り消し・キャンセル）とメッセージだけを受け付ける。今までは、事務局が団体のメンバーを兼ねると両方の操作が並ぶので、絞れなかった。
- 空き状況の action は、両方の画面で予約の作成・変更を受け、事務局の操作は事務局の画面でだけ受ける。
- ダッシュボードの確認済みにする操作は、`/` では団体側として、`/staff` では事務局として行う。
- 絞ったうえで、許されるかはユースケースが決める。ルートで絞るのは、画面に出していない操作を受け付けないためである。

### 15. 画面の中のリンクは、開いている画面の URL にする

- 予約の詳細・予約の変更・団体管理・空き状況・予約の作成への URL を組み立てる関数は、どちらの画面かを引数に取る。予約の詳細の URL を組み立てる関数が 2 つあった（`app/domain/reservation` と `app/lib/reservation-paths.ts`）ので、1 つにする。
- 事務局だけの画面（事務局のダッシュボード・予約の承認・団体の管理・操作履歴など）からは事務局の画面へ、利用者だけの画面からは利用者の画面へ、両方に置く画面からは開いている画面へリンクする。「予約一覧へ戻る」などの戻り先も、開いている画面の一覧にする。
- 団体管理で自分を団体から外したときは、利用者の画面なら事務局でもダッシュボードへ戻し、事務局の画面ならそのまま残す（UC-011）。
- `AppArea` と、URL から画面を決める関数は `app/lib/app-area.ts` に移す。メールを組み立てるドメインやサーバーのルートからも使うので、アイコンを持つ画面の部品（`app/components/layout/`）には置かない。

### 16. 切り替えは、開いている画面に当たるものへ移す

- 両方に置く画面（決定 10）を開いているときは、切り替えでもう一方の画面の同じものへ移す。予約の詳細なら同じ予約、団体管理なら同じ団体、空き状況なら同じ施設と日である。それ以外の画面では、今までどおりもう一方の画面のダッシュボードへ移る。
- 空き状況で引き継ぐのは施設と日だけで、欄で開いているもの（予約・仮の枠・変更）は引き継がない。欄の作り方と受け付ける操作が画面で変わるためである（決定 13・14）。ほかのクエリ（操作履歴のページなど）も引き継がない。
- 2 段階目より前に届いたメールのリンク（`/reservations/:id`）を事務局が開いても、切り替えを 1 回押せば、事務局の画面で同じ予約を開ける。
- 事務局の画面から利用者の画面へ移ると、所属していない団体の団体管理は「見つからない」（COND-011）になり、所属していない団体の予約の詳細は公開されている項目だけになる。事務局でない利用者と同じ見え方なので（COND-030 の (1)）、そのままにする。
- 予約の一覧と団体の一覧は、利用者の画面（自団体・所属団体）と事務局の画面（全団体）で別の画面なので、ダッシュボードへ移る。

### 17. 通知メールのリンクは、受け取る立場の画面にする

COND-030 の (5) のとおりにする。

- 予約の通知（EVT-001〜007・EVT-012・EVT-017）: 団体側の宛先（申請者・団体の管理者）には利用者の画面の予約の詳細を、事務局の宛先には事務局の画面の予約の詳細を載せる。両方にあたる人には、今と同じく団体側として 1 通だけ送る（宛先を決める処理で、事務局の宛先から団体側の宛先を除いてある）。
- メッセージの通知（EVT-008）: 団体側の送信は事務局に届くので事務局の画面を、事務局としての送信は団体側に届くので利用者の画面を載せる。
- 自団体の予約のカレンダー（UC-039）に載せるリンクは、利用者の画面のままにする。購読するのは所属メンバーである。

### 18. 表示も、開いている画面の立場に従う

- 予約の詳細・団体管理の loader は、画面に渡す「事務局として見ているか」を、セッションの `is_staff` ではなく画面から決める。利用者の画面では、事務局であっても、事務局として送られたメッセージの送信者と、事務局権限による操作の操作者を「事務局」とだけ出す（COND-030 の (2)）。
- 団体管理の購読 URL の欄（UC-039）は、利用者の画面で所属しているときだけ出す。事務局の画面では所属を読まないので（決定 12）、所属していても出ない。

## 採らなかった案

- **立場を Cookie やセッションに持つ（モードの切り替え）。** タブごとに違う立場で操作できず、メールのリンクやブックマークがどちらの立場で開くかが、そのときの状態で変わる。見えない状態が権限を左右する。
- **ナビだけを切り替え、URL は分けない。** サーバーがどちらの立場の操作か分からず、2 段階目の「立場を画面で決める」ができない。
- **ログインしている事務局が `/` を開いたら `/staff` へ転送する。** 決定 4 のとおり。
- **切り替えに件数の合計を出す。** 決定 5 のとおり。
- **「どちらでもない」画面では、いつも利用者の画面のナビを出す。** 事務局の画面から予約の詳細を開くたびにナビが変わり、戻り先が分からなくなる（決定 3）。
- **同じルートのファイルを 2 つの URL に登録し、どちらの画面かを URL から読む。** ファイルは減るが、「画面は 1 つにつき 1 フォルダ」（`app/routes.ts`）が崩れ、どちらの画面のルートかがファイルから読めなくなる（決定 10）。
- **ユースケースの引数 `isStaff` の名前を、立場を表す名前に変える。** 両方に置く画面のほか、事務局だけの画面のユースケースまで書き換えることになる（決定 12）。
- **切り替えは、いつももう一方の画面のダッシュボードへ移す。** 前に届いたメールのリンクや、団体から問い合わせのあった予約を事務局の画面で見るには、探し直すことになる（決定 16）。

## 影響

- 外枠（`app/routes/app-layout/`）とナビ（`app/components/layout/`）は、事務局かどうかではなく、どちらの画面かを受け取って項目を決める。
- ダッシュボードの loader・action・コンポーネントを `/` と `/staff` に分ける。事務局のダッシュボードを開く E2E（UC-001・UC-006・UC-014・UC-037）は、`/staff` を開くように直す。
- ログイン後の既定の行き先が `/start` になる。事務局がログインした後の URL は `/staff` になる。
- Cookie を読む処理（`findCookieValue`）を `app/lib/` に出し、前回のログイン方法・サイドバーの開閉・最後に使った画面で共用する。
- 2 段階目から、団体に所属する事務局が利用者の画面で操作すると、記録（`acted_as_staff`・`sent_as_staff`）と予約の作り方・変え方が団体のメンバーと同じになる。事務局として操作するには、事務局の画面を開く。
- 事務局だけの画面のリンクは、事務局の画面の URL へ変わる。事務局が予約の詳細・空き状況・団体管理を開く E2E は、`/staff/...` を開くように直す。
- 2 段階目より前に届いたメールのリンクは、利用者の画面を開く（決定 16）。

## 残っていること

- 事務局が自分の所属する団体の仮予約を承認することは、今と同じく妨げない（COND-030 の (6)）。
