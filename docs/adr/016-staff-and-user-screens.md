# ADR-016: 事務局の画面と利用者の画面を URL で分け、立場は開いている画面で決める

## ステータス

提案 (2026-10-27)

Issue #238 を受けて決める。業務のルールは COND-030（`rdra/contexts/reservation-approval.md`）に書いてある。作業は 2 段階に分ける（決定 1）。1 段階目（外枠・ナビ・ダッシュボードを分け、切り替えを付ける）で決めたことを決定 1〜9 に書く。2 段階目で、立場を画面から組み立てるときに、この ADR に書き足す。

## コンテキスト

今は、事務局の人には、利用者向けのナビ・ダッシュボードと、事務局向けの機能が同じ画面に並んでいる（#238）。

- **画面が複雑に見える。** 事務局から見ると、ふだん使わない団体の機能が混ざる。スマホでは「その他」に 6 項目が入る。
- **どちらの立場で操作しているのか分からない。** 団体と事務局の両方に所属する人の立場を、システムが所属から推し量っている。自分の団体の予約にメッセージを送ると必ず団体側の送信になり、予約を変えると必ず事務局の直接変更になる。
- **コードが複雑になっている。** ダッシュボードの loader とコンポーネントが、事務局用と一般用の 2 つの画面を出し分けている。権限の判定にも、所属を読むものと読まないものが 2 本ずつある。

COND-030 は、事務局の画面と利用者の画面を分けて切り替えて使い、立場は開いている画面で決める、と定めた。この ADR は、それを URL・外枠・ダッシュボードでどう作るかを決める。

## 決定

### 1. 2 段階に分ける

1. **業務のルールは変えない。** 外枠・ナビ・ダッシュボードを利用者の画面（`/`）と事務局の画面（`/staff`）に分け、切り替えを付ける。予約の詳細などは、今までどおり両方の立場の操作を出す。
2. **立場を画面で決める。** 予約の詳細・空き状況・予約の作成と変更・団体管理に事務局の画面のルートを足し、操作する人（`Actor`）を画面から組み立てる。通知メールのリンクを直す。所属を読む・読まないの 2 本立てなど、両方の立場を前提にしたコードを片付ける。

1 段階目だけでも、事務局の人の画面は使いやすくなる。2 段階目は、ユースケースに渡す値が変わるので、分けたほうが見直しやすい。

### 2. どちらの画面かは URL のパスで決める

- `/staff` と `/staff/...` は事務局の画面とする。`/staff-invitations/...`（事務局招待の承諾）は、招待される人がまだ事務局ではないので、事務局の画面に含めない。
- 利用者の画面は、`/`（ダッシュボード）・`/reservations`（自団体の予約一覧）・`/groups`（所属団体の一覧）・`/groups/new`（団体の登録）とする。
- 両方に置く画面（空き状況・予約の作成・予約の詳細・予約の変更・団体の管理）は、1 段階目では利用者の画面の URL しか無い。これらと、どちらにも属さない画面（アカウント設定・招待の承諾）は、外枠を決めるうえで「どちらでもない」として扱う（決定 3）。2 段階目で事務局の画面の URL を足すと、両方に置く画面もどちらかに決まる。
- Cookie やサーバーの状態には持たない。タブを 2 つ開いて別々の画面で操作しても食い違わず、メールのリンク・ブックマーク・戻るボタンがそのまま動く。サーバーはリクエストのパスだけでどちらの画面か分かる。

### 3. 「どちらでもない」画面では、最後に使った画面のナビを出す

事務局の画面から予約の詳細やアカウント設定を開いたときに、ナビが利用者の画面のものに変わると、どこにいるのか分からなくなる。そのため、「どちらでもない」画面では、そのタブで最後に開いていた画面のナビを出す。

- 最後に開いていた画面は、外枠のコンポーネントが覚えておく（React の状態）。決まった画面を開くたびに更新する。
- ページを読み込み直したときに備えて、ブラウザの Cookie（`iclub-reserve.last-area`。値は `staff` か `user`）にも書く。外枠の loader はこれを読んで、最初の描画を決める。Cookie が無ければ、事務局には事務局の画面のナビを出す（決定 4 と同じく、初めては事務局の画面）。
- Cookie に書くのは事務局の人だけで、ブラウザから書く。1 年保つ。中身は「どちらの画面か」だけで、誰のものかは分からない。
- この Cookie は、ナビの出し方とログイン後の行き先（決定 4）にしか使わない。権限の判定と、操作する人の立場には使わない（COND-030 の (4)）。書き換えられても、出るナビが変わるだけである。

### 4. ログイン後は `/start` を通し、前回使っていた画面のダッシュボードへ送る

- 画面を持たないルート `/start` を足し、その loader で行き先を決めて転送する。事務局には、Cookie（決定 3）が `user` なら `/` を、それ以外（`staff`・無い）なら `/staff` を開かせる。事務局でない人は、いつも `/` へ送る。
- ログイン後の既定の行き先（遷移先の指定が無いとき）を `/` から `/start` に変える。ログイン・お名前の登録・パスキーの案内は、どれも最後にこの行き先へ進むので、`/start` の判定だけで済む。
- 遷移先のパスが `/` のときも（`/?utm_source=mail` のようにクエリが付いていても）、既定と同じに扱って `/start` へ送る。ログインしていない人がアドレスを打って開くのは `/` だからである。
- ホーム画面に追加したアプリ（PWA）も、開くと `/start` を通す（`start_url`）。マニフェストに `id` を書いてあるので、`start_url` を変えても別のアプリとはみなされない（ADR-011）。
- ログインしている人が `/` を直接開いたときは、URL のとおり利用者の画面のダッシュボードを出し、転送しない。`/` を転送すると、事務局が利用者の画面のダッシュボードを開けなくなるうえ、決定 2 の「URL で決める」が崩れる。

### 5. 切り替えは「その人が行ける画面の一覧」から作る

- 行ける画面の一覧（事務局なら利用者の画面と事務局の画面、そうでなければ利用者の画面だけ）を返す関数を 1 つ置き、切り替えはそれを並べて描く。2 つ以上あるときだけ出す。「事務局か、そうでないか」の 2 択で書かないのは、システム運用の画面（#188）を 3 つ目として足せるようにするためである。
- PC・タブレットではサイドバーの上（ロゴの下）、スマホでは上部の帯の右端に置く。どの画面からも押せ、いまどちらの画面にいるかを常に示す。
- 押すと、もう一方の画面のダッシュボードへ移る（リンク）。開いている画面に当たるものへは移さない。1 段階目では、両方に置く画面にまだ事務局の画面の URL が無いためである。
- もう一方の画面のナビに件数が付いていれば、切り替えのその画面に点の印を付ける。数字にしないのは、「その他」の印と同じく、種類の違う件数（承認待ちの予約と団体など）を足しても意味が無いためである。どの件数かは、移った先のナビで分かる。

### 6. ナビの項目は画面ごとに持つ

| 画面         | サイドバーの項目                                                                                                             | ボトムバーに直接並べる項目                   | 入口の文言 |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- | ---------- |
| 利用者の画面 | 「ダッシュボード」「空き状況」「予約」「所属団体」                                                                           | 「ダッシュボード」「空き状況」「予約」       | 予約を申請 |
| 事務局の画面 | 「ダッシュボード」「空き状況」「予約の承認」「団体の管理」「施設・設備の管理」「カレンダー購読」「操作履歴」「事務局の管理」 | 「ダッシュボード」「空き状況」「予約の承認」 | 予約を作成 |

- 事務局でない人のナビは、今と変わらない。
- 入口の文言は、開いている画面で決める（今は事務局かどうかで決めている。ADR-014 決定 9）。1 段階目では、入口の先のフォームはまだ事務局に両方の作り方を出す。
- 空き状況は両方の画面に置く（COND-030 の (3)）。1 段階目では、どちらのナビからも `/availability` を開く。

### 7. ナビの件数は画面ごとに数える

- 利用者の画面のダッシュボード: 団体側の未読と、自分宛ての招待の数（今の事務局でない人と同じ）。
- 事務局の画面のダッシュボード: 団体からの未読メッセージのある予約の数。
- 予約の承認・団体の管理: 今と同じ。

今は事務局のダッシュボードの件数に、この 3 つをすべて足している。ダッシュボードが分かれるので、件数もそれぞれのダッシュボードに並ぶ行の数にそろえる。

### 8. ダッシュボードを 2 つのルートに分ける

- `/`（`app/routes/home/`）は利用者の画面のダッシュボードとし、事務局が開いても事務局でない人と同じものを出す（SCR-022）。
- `/staff`（`app/routes/home/staff/`）は事務局の画面のダッシュボードとし、今の事務局用の区画を移す。「所属団体」の区画（自分の団体の未読・今後の予約・招待）は出さない。それらは利用者の画面で見る。
- loader とコンポーネントで事務局かどうかを分岐していたのをやめ、ルートごとに 1 つの画面にする。仮予約の承認・却下は `/staff` の action だけが受ける。
- `/staff` の loader は、区画を読む前に事務局かどうかを確かめ、事務局でなければ 403 にする。区画は読めなくても画面を開く作りなので、先に確かめないと、事務局でない人に区画が空のダッシュボードを見せてしまう。
- 利用者の画面のダッシュボードの「団体の最近の動き」は、事務局が開いても事務局でない人として読む（操作者を「事務局」と出す。COND-030 の (2)）。今まで事務局には出していなかった区画なので、1 段階目から画面の立場に従わせても、今の振る舞いは変わらない。

### 9. 1 段階目では、ほかの画面の立場は変えない

予約の詳細・空き状況・予約の変更・団体の管理・メッセージは、今までどおりセッションの `is_staff` で判定する。事務局が利用者の画面のナビから開いても、事務局の操作が出る。2 段階目で、これらに事務局の画面のルートを足すときに直す。

## 採らなかった案

- **立場を Cookie やセッションに持つ（モードの切り替え）。** タブごとに違う立場で操作できず、メールのリンクやブックマークがどちらの立場で開くかが、そのときの状態で変わる。見えない状態が権限を左右する。
- **ナビだけを切り替え、URL は分けない。** サーバーがどちらの立場の操作か分からず、2 段階目の「立場を画面で決める」ができない。
- **ログインしている事務局が `/` を開いたら `/staff` へ転送する。** 決定 4 のとおり。
- **切り替えに件数の合計を出す。** 決定 5 のとおり。
- **「どちらでもない」画面では、いつも利用者の画面のナビを出す。** 事務局の画面から予約の詳細を開くたびにナビが変わり、戻り先が分からなくなる（決定 3）。

## 影響

- 外枠（`app/routes/app-layout/`）とナビ（`app/components/layout/`）は、事務局かどうかではなく、どちらの画面かを受け取って項目を決める。
- ダッシュボードの loader・action・コンポーネントを `/` と `/staff` に分ける。事務局のダッシュボードを開く E2E（UC-001・UC-006・UC-014・UC-037）は、`/staff` を開くように直す。
- ログイン後の既定の行き先が `/start` になる。事務局がログインした後の URL は `/staff` になる。
- Cookie を読む処理（`findCookieValue`）を `app/lib/` に出し、前回のログイン方法・サイドバーの開閉・最後に使った画面で共用する。

## 残っていること

- 2 段階目（決定 1）。
- 切り替えで移るのは、もう一方の画面のダッシュボードだけである。2 段階目で両方に置く画面に事務局の画面の URL を足したら、予約の詳細なら同じ予約の詳細へ、のように開いている画面に当たるものへ移すかを決める。
- 事務局が自分の所属する団体の仮予約を承認することは、今と同じく妨げない（COND-030 の (6)）。
