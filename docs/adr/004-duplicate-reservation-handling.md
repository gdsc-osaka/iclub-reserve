# ADR-004: 重複予約時の処理方針 — キャンセル先行を強制する

- **ステータス**: Accepted
- **決定日**: 2026-03-18
- **決定者**: GDG on Campus Osaka 開発チーム
- **関連 RDRA**: COND-001, UC-002, UC-005, UC-006, UC-008

---

## コンテキスト

同一施設・同一時間帯に承認済み予約が存在する場合、新規申請・変更・承認・事務局直接作成のすべてで重複チェックが必要になる（COND-001）。

重複が発生するケースとして以下が想定される。

- 団体が既存の承認済み予約と重複する時間帯に仮予約を申請する（UC-002）
- 事務局が承認時に他の承認済み予約と重複していることに気づく（UC-006）
- 事務局が優先度の高いイベント予約を直接作成しようとする（UC-008）
- 団体が承認済み予約の施設・日時を変更した結果、他の承認済み予約と重複する（UC-005）

この重複をシステムがどのように扱うかを決定する必要がある。

## 選択肢

| 案 | 方式 | 採否 |
|----|------|------|
| **A（採用）** | 重複が存在する場合はエラーを返し、操作者が先に既存予約をキャンセルすることを強制する | ✅ |
| B | システムが自動的に既存の仮予約を一括キャンセルして新しい予約を通す | ❌ |
| C | 重複を許容し、事務局が後から調整する | ❌ |

### 案B を却下した理由

システムが暗黙に他団体の予約をキャンセルすることは、以下の問題がある。

- キャンセルされた団体へ理由を説明する機会が失われる（COND-002 の精神に反する）
- 事務局の判断と意思表示（理由入力・通知）を必要とする設計が、優先順位の制御（GOAL-002）の目的に沿っている
- 自動キャンセルの対象選定ロジック（どの予約を消すか）が複雑になる

### 案C を却下した理由

重複を許容すると施設の物理的な利用可否と予約状態が乖離し、予約システムとしての信頼性が損なわれる。

## 決定

**重複が存在する場合はエラーを返し、操作者が先に既存予約をキャンセルしてから再操作することを強制する。**

### 適用箇所

| ユースケース | 重複チェックのタイミング |
|------------|----------------------|
| UC-002: 仮予約申請 | 申請時 |
| UC-005: 承認済み予約の施設・日時変更 | 変更保存時 |
| UC-006: 仮予約の承認 | 承認実行時 |
| UC-008: 事務局による直接作成 | 作成時 |

### エラー時の挙動

重複が検出された場合、システムは操作を拒否してエラーを返す。エラーメッセージには重複している既存予約（施設名・日時・団体名）を提示し、操作者が判断できるようにする。

## 影響・トレードオフ

| 項目 | 内容 |
|------|------|
| 操作ステップ数 | 事務局が優先予約を直接作成する場合、既存予約を先にキャンセルする手順が必要になる。ただしこれは意図的な設計で、事務局の明示的な判断を記録に残す |
| 仮予約の扱い | 重複チェックは「承認済み予約」に対してのみ行う。仮予約同士は重複を許容し、承認時点でチェックする |
