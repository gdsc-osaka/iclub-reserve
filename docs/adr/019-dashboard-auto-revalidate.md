# ADR-019: ダッシュボードを自動で読み直す

## ステータス

承認 (2026-11-13)

## コンテキスト

Issue #277 を受けて決める。

事務局のダッシュボード（`/staff`）は PC で開いたままにされることが多く、ほかの事務局や団体の操作（仮予約の申請、メッセージの送信、団体の登録など）があっても、画面を自分で読み直すまで反映されない。一方、利用者のダッシュボード（`/`）は、スマートフォンで開いて用を済ませたら閉じる使い方が中心である。

開いたままの画面で新しい情報に気づけるようにしつつ、Cloudflare D1 の無料枠（1 日 500 万行の読み取り）に収めるための読み直し方式を定める。

## 決定

### 1. 事務局は 5 分ごと、利用者は戻ったときだけ読み直す

- **事務局のダッシュボード（`/staff`）**: 画面が表示されている間、5 分ごとに自動で読み直す。画面に戻ってきたとき（タブがアクティブになったとき・オンラインに復帰したとき）は、前回の読み込みから 30 秒以上経過していれば直ちに読み直す。
- **利用者のダッシュボード（`/`）**: 定期的には読み直さない。画面に戻ってきたときの読み直し（前回の読み込みから 30 秒以上経過）のみ行う。利用者は開いて閉じる使い方が中心であり、相手の動きはメール通知でも届く（UC-037）。また、ホーム画面に追加したアプリ（PWA）は裏に回っても画面を保持し続けるため、戻ってきたときの読み直しで十分である。

### 2. useRevalidator().revalidate() で読み直す

読み直しは React Router の `useRevalidator().revalidate()` を用いる。

- **外枠の件数との整合**: 同じ URL の読み直しでは外枠（app-layout）の loader も再実行される（`app/routes/app-layout/nav-counts.ts` の `shouldRecountNavCounts` の 3）。これにより、ナビゲーションのバッジ件数とダッシュボードのタイルの件数が常にそろう。
- **効率的な通信**: single fetch により、1 回の再検証は Cloudflare Worker への 1 つのリクエストにまとまる。Service Worker は画面遷移（`mode: "navigate"`）のみを扱うため、データの読み込み（`.data`）には干渉しない（ADR-011 決定 3）。
- **基準時刻の更新**: 基準時刻 `now` を loader 側で決定して返しているため、画面の読み直しによって相対時刻の表示、今日の予約における現在時刻の線、日付表示も新しくなる。

### 3. 操作の邪魔や無駄になる状況では読み直さない

次のいずれかに当てはまる状況では、自動の読み直しを行わない。

- **ダイアログが開いているとき（`[role="dialog"], [role="alertdialog"]` が DOM に存在）**: ほかの事務局が先に承認・却下した予約は、読み直すと行ごと消え、入力中だった却下の理由なども消えてしまうためである。Radix UI（shadcn/ui）の Dialog・AlertDialog・Sheet は開いている間だけ DOM に要素を配置するため、セレクタで判定できる。ダイアログごとに開閉を通知する仕組みを作るより単純で漏れがない。
- **画面の移動中・fetcher の送信中や読み込み中・読み直しの途中（ビジー状態）**: 完了後に React Router 自体が loader を読み直すため、二重に重ねない。
- **オフラインのとき**: 読み直しが通信失敗し、エラー画面に切り替わってしまうのを避けるためである。
- **タブが裏にあるとき（`document.visibilityState !== "visible"`）**: 見ていない画面のために D1 の読み取り枠を消費しない。

画面に戻ってきたときの読み直しをこれらの理由で見送ったときは、読み直せるようになってから 15 秒のうちに読み直す（利用者のダッシュボードでも）。ダイアログを「やめる」で閉じたときに、次に戻ってくるまで古い画面のままにしないためである。

### 4. 事務局のダッシュボードに読み込んだ時刻を出す

事務局のダッシュボードのヘッダーの日付の横に、読み込んだ時刻を「14:32 時点」の形式で表示する。これにより、自動更新が順調に動いているか、停止していないかを一目で確認できるようにする。

### 5. 通信のエラーは root の ErrorBoundary で受け、接続が戻れば元の画面に戻す

root の `ErrorBoundary` で通信のエラー（`TypeError` で "Failed to fetch" などのブラウザごとの文言）だけを見分け、「接続できませんでした」の画面を出す。`online` のイベントと 30 秒ごとに読み直し、成功すれば元の画面に戻る。

これまでは、通信が一瞬切れたときに読み直すと root のエラー画面に替わり、タイマーも止まって、自分で読み込み直すまで戻らなかった。スリープから戻った直後のノート PC で起きやすい。

外枠（app-layout）には置かない。読み直しでは root の loader も一緒に失敗し、エラーは外枠ではなく root に届くためである。

### 6. 間隔を 5 分にした根拠

ダッシュボード表示時の D1 読み取り行数の計測結果は次のとおりである。

| 予約の件数 | 索引なし    | 索引あり（PRAGMA optimize 後） |
| ---------- | ----------- | ------------------------------ |
| 1,000 件   | 約 4.6 万行 | 約 1,300 行                    |
| 4,000 件   | 約 64 万行  | 約 4,100 行                    |

※ `/staff` を 1 回読んだときの D1 の rows_read（外枠の件数を含む）。予約 1 件につき操作履歴 3 件、3 件に 1 件はメッセージ 2 通のテスト用データで測定。

D1 の無料枠は 1 日 500 万行である。1 日 12 時間ブラウザを開いたままにした場合、60 秒ごとの更新では 720 回の読み出しとなり、1 タブだけで 1 日約 300 万行を消費し、事務局が 2 人開けば無料枠を超える。一方、5 分ごとなら 144 回となり、1 タブで約 60 万行に抑えられる。

索引は #314（マイグレーション 0026）で足した。索引が無いと、重なりの判定が承認待ちの行ごとに全予約を読むため、予約の件数の 2 乗で増える。将来 Workers Paid プランへ移行した際には、間隔をさらに短縮してもよい。

## 採らなかった案

| 案                                                                   | 採らなかった理由                                                                                                                     |
| -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| Durable Objects と WebSocket・SSE で知らせる                         | 書き込みのすべての経路に知らせる処理を足す必要がある。求めているのは秒単位の速さではない。                                           |
| 最後に変わった時刻だけを返す軽い入口を作り、変わったときだけ読み直す | 区画を足すたびに「何が変わったら知らせるか」をそろえ続ける必要があり、漏れると更新されない。費用が足りなくなったときの次の手とする。 |
| clientLoader で通信のエラーを受け、前のデータを返す                  | 外枠の loader にも要り、single fetch の 1 回のリクエストにまとまらなくなる。                                                         |
| 利用者のダッシュボードも定期的に読み直す                             | 決定 1 の理由。                                                                                                                      |
