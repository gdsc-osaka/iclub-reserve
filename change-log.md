# 要件変更履歴

RDRA 成果物（`rdra/`）と PRD（`docs/prd.md`）の変更を記録する。

現在どこまで実装されているかは [`docs/implementation-status.md`](docs/implementation-status.md) を参照。こちらは追記専用の履歴、あちらは現状を写した表である。

## 2026-09-09 — レビュー指摘への対応

### 背景

PR のレビューで、成果物どうしの矛盾と記述の曖昧さについて7件の指摘を受けた。いずれも実在を確認したうえで対応した。要件の追加・削除は無い。

### 変更内容

| 指摘                                                                                                                            | 対応                                                                                                                                                              |
| ------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| COND-011（団体の存在秘匿）と COND-008（予約の可視範囲）が矛盾する。他団体の予約に団体名を出せば、その団体の存在は推測できる     | COND-011 の対象を「団体そのものを引く経路（詳細取得・検索・一覧）」に限定した。予約に付随して表示される団体名は COND-008 の定めによるもので対象外であることを明記 |
| COND-011 を厳密に適用すると、SCR-016 で招待元の団体名を表示できない                                                             | 有効かつ未失効の招待を提示した受信者を例外として明記。失効・取り消し・不存在の場合は通常の未所属者と同じ応答に戻すことも併記                                      |
| COND-004 が「登録時の制限」と「既存ユーザーのログイン例外」を混ぜて書いており、メールアドレス変更にどちらが効くのか読み取れない | COND-004 を場面ごとに分けて記述。ログイン向けの例外をメールアドレス変更へ流用してはならないことを明示し、実装課題12へも反映                                       |
| INFO-006.name が必須とされながら、アカウント作成直後は未設定と書かれておりデータ形状が決まらない                                | NULL は許さず、未設定は空文字で表すことを明記。空白のみの値も未設定として扱う（`isProfileCompleted` の判定と一致）                                                |
| INFO-006.email の説明が、保存値の制約と入力時の制約を区別していない                                                             | 保存する値のドメインは制限せず、制限は作成時と変更時の入力に対して働くことを明記                                                                                  |
| BIZ-006 の本文と BUC-020 が、ドメイン制限を「利用できる人の条件」と読める書き方になっている                                     | 「アカウントを作れる人の条件」であることを本文に明記し、BUC-020 にもサブドメインを含む旨を追記                                                                    |
| PRD の Mermaid ラベルに実際の改行が入っており、同じ文書の他のラベルと記法が揃っていない                                         | `\n` 記法へ統一                                                                                                                                                   |
| ADR-001 の平文コードフェンス5箇所に言語識別子が無い（markdownlint MD040）                                                       | `text` を付与                                                                                                                                                     |

## 2026-09-09 — 実装との乖離解消（第1回: 矛盾の解消）

### 背景

ドキュメント（`rdra/`・`docs/prd.md`）とコードの突き合わせを行い、**矛盾13件・文書に無い実装9件・未実装の要求多数・メタ情報の陳腐化**を検出した。このうち「どちらが正か判断が要る矛盾」を対象に、方針を決めて成果物へ反映した。

未実装の要求（メッセージ機能・Google Calendar 連携・予約の更新系・メール通知など）は、仕様と実装のずれではなく実装の進捗の問題であるため、今回の改訂対象には含めていない。

### 決定と変更内容

| 論点             | 決定                                                                       | 変更した成果物                                                 |
| ---------------- | -------------------------------------------------------------------------- | -------------------------------------------------------------- |
| ログイン方式     | 実装（認証コード＋パスキー）を正とし、パスワード認証を仕様から削除         | REQ-032 改訂、REQ-034 新設、BUC-020〜022、UC-019〜021          |
| 団体の作成       | 作成は誰でも可・利用は事務局の承認制、という折衷を採用                     | REQ-016 改訂、COND-006 新設、STATE-002 新設                    |
| 団体の状態       | `is_active`（2値）を `status`（pending/enabled/disabled）へ                | INFO-003、STATE-002、REQ-021                                   |

| メンバー追加方式 | 招待・承諾方式を正とする（実装に合わせる）                                 | REQ-017 改訂、INFO-007 新設、BUC-023、UC-022、SCR-016、EVT-014 |
